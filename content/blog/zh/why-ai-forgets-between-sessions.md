AI 在一个聊天中记得细节，换到新聊天却答不上来，背后可能是完全不同的系统。它未必像人一样“忘记”了：应用可能没有把旧对话提供给模型，记忆功能可能未启用，检索可能没找到正确资料，隐私政策也可能有意禁止复用。

本文只负责技术诊断：解释各层机制，提供可复现测试，再把症状映射到解决方法。姊妹篇[为什么 AI 每轮会话都会忘记你](/zh/blog/why-ai-forgets-every-session)负责连续性问题带来的工作影响与工具选择。明确主责后，就不会把所有问题都误判为同一种“记忆失效”。

## 五种常被统称为“AI 记忆”的能力

| 层面 | 作用 | 常见生命周期 | 典型故障 |
|---|---|---|---|
| 上下文窗口 | 容纳当前模型调用可见的 token | 一次请求或应用组装的活跃对话 | 旧内容被省略或压缩 |
| 会话历史 | 保存消息，以便应用重新打开或再次提供 | 直到删除或触发保留政策 | 新聊天没有带入旧历史 |
| 长期记忆 | 保存选中的偏好或事实，供未来复用 | 跨聊天，直到修改或删除 | 没写入、过期或未被选中 |
| 检索 | 运行时查找相关文件、消息或记录 | 每次查询 | 查询、权限、索引、排序或版本错误 |
| 持久项目状态 | 记录决定、成果、进度、审批与外部 ID | 跨会话和执行者 | 状态只存在于对话文字，未写检查点 |

这些层面可以同时存在。产品可能保存聊天历史，但不会把所有旧消息交给新聊天；可以使用偏好记忆，却不会自动打开旧项目文件；也可能检索到文档，却漏掉文档写成之后的新决定。

## 上下文窗口不会自动产生跨会话记忆

语言模型根据应用为本次调用组装的输入生成回复。输入可以包含指令、近期消息、文件、检索片段、工具结果以及应用提供的记忆。上下文窗口只是这些输入与输出的容量，不是一座由模型自行带到下一轮会话的数据库。

长对话中，应用可能不再发送早期消息，或者先摘要、压缩历史，以免超出窗口。即使容量足够，相关性和注意力仍会影响结果：一个事实出现在上下文中，也不代表模型一定正确使用。

因此，更大的上下文窗口可以减少单项任务中的截断，却不能决定关闭对话后哪些信息继续存在。

## 会话历史是存储，不等于必然召回

聊天出现在侧边栏，只能说明应用保存了足以重新打开它的数据，并不代表每个新聊天都会自动拿到所有旧消息。全量带入既昂贵、噪声大，也可能不符合隐私预期。

- **继续同一聊天：**应用可以重发或摘要这段历史。
- **新建聊天：**可能只带入全局指令、已选记忆、项目资料或检索到的旧内容。
- **临时或隐私模式：**产品可能有意关闭历史和记忆写入。

OpenAI 当前的[临时聊天文档](https://help.openai.com/en/articles/8914046/temporary-chat-in-chatgpt)说明了产品设置为什么重要：临时聊天与普通已保存聊天的行为不同，并且在保持临时状态时不会创建或更新记忆。具体行为还取决于账户、工作区和功能状态，应检查你实际可见的控制项。

## 长期记忆具有选择性，也会出错

长期记忆通常不会把全部历史聊天复制给每次请求。产品可能提取事实、合成个人摘要，或在判断相关时搜索过去活动。

因此有四类可预测故障：

1. **写入失败：**该细节从未进入记忆。
2. **选择失败：**已经保存，但这次回复没有带入。
3. **过期：**情况已经改变，旧偏好或事实仍在影响答案。
4. **冲突：**多条记忆或资料互相矛盾。

OpenAI 当前的[记忆 FAQ](https://help.openai.com/en/articles/8590148/memory-in-chatgpt-remembering-what-you-chat-about)说明记忆摘要是一种综合结果，未必展示所有影响因素，也明确区分了保存记忆与聊天历史。Google 同样说明，Gemini 基于[历史聊天的个性化](https://support.google.com/gemini/answer/16598469?hl=en)会受账户类型、设置和功能开放范围影响。

长期记忆适合稳定偏好和重复使用的事实，却不应成为关键项目决策的唯一事实源。

## 检索也不等于记忆

检索是在需要时让模型访问外部资料，来源可能是文件、数据库、搜索索引、邮箱或项目工作区。文件存在不等于一定能被正确找到，检索还取决于：当前身份是否有权限、资料是否已索引或可由工具访问、查询是否描述准确、排序是否找出正确片段、资料版本是否最新，以及模型是否真正使用了返回内容。

当检索失败时，用户常说“AI 忘了”，但真正要修的可能是访问规则、陈旧索引、混乱的资料结构、含糊命名或缺少引用，而不是记忆开关。

对重要工作，应要求系统标注使用的文件、记录、时间戳或对话。没有来源证据的流畅回答，无法区分真正召回与临场编造。

## 持久状态才适合承载持续工作

偏好放入记忆，项目事实放进维护中的事实源，流程进度放入结构化状态。

持久状态可以记录：任务 ID 与阶段、已确认的要求和决定、成果位置和版本、完成与待办步骤、审批和政策版本、工具结果与外部副作用 ID、未决问题和下一步行动。

长时运行的 Agent 需要检查点和交接成果，因为对话文字不是可靠的运行记录。如果另一个人或 Agent 无法仅凭保存的状态继续工作，必须重读并猜测整段聊天，连续性设计就还没完成。

## 一套可复现的记忆诊断

不要用模型可能猜到的常见个人信息测试。选择唯一且无敏感性的字符串，例如 `cedar-orbit-741`。

### 测试一：活跃上下文保留

1. 新建普通聊天，发送：“本次测试的项目代号是 `cedar-orbit-741`。”
2. 再发送若干无关消息。
3. 在同一聊天中询问项目代号。

若失败，问题发生在活跃对话内部：可能是截断、压缩、指令冲突或模型可靠性。

### 测试二：重新打开同一会话

1. 关闭或离开聊天。
2. 从历史记录重新打开完全相同的对话。
3. 再次询问代号。

若可见历史仍在但召回失败，应检查产品是否摘要了旧内容，以及该消息是否仍被提供给模型。

### 测试三：跨聊天记忆

1. 确认记忆或个性化已启用。
2. 产品支持时，在原聊天中明确要求记住代号。
3. 新建普通聊天并询问代号。

这里失败不代表历史已被删除，只能说明记忆写入、选择、账户资格或产品行为没有把它带入新聊天。

### 测试四：资料检索

1. 在一份命名清楚的测试文档中写入另一个代号。
2. 按产品文档要求添加或连接该文档。
3. 提出明确指向该文档的问题。
4. 要求回答标注来源名称。

引用缺失或错误时，依次检查访问权限、索引状态、查询措辞、重复文件和文档版本。

### 测试五：隐私控制

在临时或非个性化模式中重复跨聊天测试，再按官方说明删除测试聊天和记忆并重复。不要假设从一个存储中删除，就会自动清除其他所有副本。

## 从症状找到正确解决方法

| 症状 | 可能层面 | 更合适的修复 |
|---|---|---|
| 长聊天中的早期指令消失 | 上下文窗口或压缩 | 缩短上下文、生成经过核对的摘要、拆分任务 |
| 重新打开同一聊天仍丢细节 | 会话组装 | 检查可见历史、保留政策与摘要行为 |
| 新聊天漏掉偏好 | 保存记忆或个性化 | 启用并检查记忆；显式保存稳定指令 |
| Agent 找不到已知文件 | 检索 | 检查身份、索引、查询、版本和引用 |
| 恢复工作时走错步骤 | 持久状态 | 在对话外保存检查点和步骤状态 |
| 系统使用过时事实 | 记忆或旧资料 | 纠正或删除记忆；给权威资料加版本 |
| 删除后仍受到该信息影响 | 多个存储 | 按实际情况清理聊天、记忆、文件和连接来源 |

## 按工作类型选择连续性方案

### 稳定偏好

使用显式指令或可检查的记忆功能，保持内容精简并定期复核。

### 有边界的项目

使用能够集中保存指令、文件与对话的项目或工作区；维护简短的决策记录和来源索引，不要只依赖原始聊天历史。

### 重复发生的运营任务

使用任务契约、结构化输入、版本化模板和确定性的事实源。工作流设计可参考[如何为重复工作构建 AI Agent](/zh/blog/how-to-build-ai-agents-for-repeated-work)。

### 长时运行或多步骤 Agent

使用持久状态、检查点、幂等工具、轨迹日志和明确的交接成果。[Agent Harness 指南](/zh/blog/what-is-an-agent-harness)进一步解释了如何让模型工作受控并可恢复。

## 隐私是连续性架构的一部分

持久记忆通过保留或复用信息减少重复，同时也带来责任：了解哪些来源会影响未来回复；分开个人、项目与组织数据；只提供任务必需的信息；复核记忆和连接应用权限；理解保留、删除、导出和工作区管理员控制；不要把密钥写进提示词或自由文本记忆；不希望连续时使用临时或非个性化模式。

删除可能需要多个步骤。OpenAI 当前文档说明保存记忆与聊天历史相互独立；Google 则说明，清除连接应用中的记忆影响，可能需要同时删除相关聊天并断开资料来源。应以所用账户类型对应的最新官方说明为准。

## 最实用的原则

不要让一个名为“记忆”的功能承担所有连续性需求。

- 当前决策使用上下文。
- 继续对话使用会话历史。
- 少量稳定偏好和事实使用保存记忆。
- 权威资料使用检索。
- 项目进度、审批与恢复使用持久状态。

只要先找出是哪一层失效，“AI 忘了”就会从神秘的模型性格变成一个可复现、可修复的工程问题。
