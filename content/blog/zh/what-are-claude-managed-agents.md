Claude Managed Agents 是 Anthropic 在 Claude Platform 上提供的托管式 Agent 运行服务，目标是承载需要多步执行、持续较长时间的任务。它不是一个新模型，也不是 Claude 聊天中的新按钮。开发团队仍需定义 Agent、工具、权限、凭据和验收标准；Anthropic 管理的是让这些组件持续运行的基础设施。

因此，“托管”不等于“无需治理”。它减少的是运行时建设，不会替团队决定什么任务值得自动化，也不会自动证明结果正确。

## 一句话理解它的架构

Anthropic 将 Agent 拆成三个可以分别管理的部分：

| 部分 | 职责 |
|---|---|
| Session | 以追加式事件历史记录动作与结果 |
| Harness | 调用 Claude，并把工具请求路由到执行环境 |
| Sandbox | 让 Claude 在隔离环境中运行代码、处理文件 |

Managed Agents 把这三部分抽象为相对稳定的接口。底层 harness 或 sandbox 可以演进，接入方不必每次推倒重建。Anthropic 在[官方工程文章](https://www.anthropic.com/engineering/managed-agents)中将其称为 “meta-harness”，强调的正是运行层与具体 Agent 实现解耦。

它属于 Claude Platform，主要面向产品、平台和工程团队。若需求只是个人问答、处理桌面文件或修改代码，Claude chat、Cowork 与 Claude Code 才是直接使用的产品形态。

## Managed Agents 真正提供了什么

它的价值不是凭空增加“自主性”，而是为长任务提供可运营的执行外壳：

- **持久会话**：事件历史不只存在于单次模型上下文中，中断后可以据此恢复状态。
- **隔离执行**：代码和文件操作发生在边界明确的 sandbox 内。
- **工具路由**：harness 接收模型的工具请求，交给获准的执行端，并留下记录。
- **权限收敛**：可以给 Agent 使用专门的、范围更小的凭据，而非沿用操作者全部权限。
- **执行追踪**：团队能检查过程，而不是只看到一个最终答案。
- **长时间运行**：运行时面向无法稳定塞进一次请求与响应的工作。

这些能力有助于“把 Agent 跑起来”，但不会替业务方验证“它是否把工作做对”。

## 它不是什么

Managed Agents 不是现成的业务流程产品。它不会自动识别审批规则、整理混乱数据、判断哪个系统才是真实来源，也不会替你定义完成标准。

Sandbox 也不等于业务安全。它能限制代码在哪里运行，却不能判断退款对象是否选错、邮件是否发给错误客户、审批依据是否已经过期。只要 Agent 可以写入外部系统，重复执行、错误选项和陈旧状态都可能产生真实影响。

产品范围、预览标签、配额与价格也可能变化。正式设计前，应回到[Claude Platform 官方文档](https://platform.claude.com/docs/en/home)核对当时的端点、账号与地区资格、限制和计费信息，不要把发布初期的 beta header、价格或模型清单写死为长期前提。

## 与 Cowork、Claude Code、普通对话有什么区别

| 形态 | 更适合什么 | 主要使用者 | 典型边界 |
|---|---|---|---|
| Claude chat | 问答、分析、起草 | 普通用户 | 一次对话 |
| Claude Cowork | 跨文件、跨连接应用的委派任务 | 知识工作者 | 一项需要复核的桌面工作 |
| Claude Code | 代码库与终端任务 | 开发者、技术操作者 | 本地或远程开发环境 |
| Claude Managed Agents | 对外或对内提供自定义 Agent 服务 | 产品、平台团队 | 程序化托管运行时 |

Cowork 与 Claude Code 是人直接操作的 harness；Managed Agents 是承载自定义 harness 的基础设施。选型问题不是“谁更聪明”，而是：团队是在寻找一个可直接工作的界面，还是要构建一个由 Agent 驱动的产品。

如需理解运行层的职责，可继续阅读[什么是 Agent Harness](/zh/blog/what-is-an-agent-harness)；如果重点是 Agent 如何取得外部数据与动作能力，可参考 [AI Agent Connectors 详解](/zh/blog/ai-agent-connectors-explained)。

## 哪些任务适合托管 Agent

适合的任务通常具备五个条件：目标可重复、输入可机器读取、工具范围有限、中间过程可观察、最终结果可由人或规则验证。文档接收、代码库维护、结构化调研、对账和进入人工队列的初筛，通常比开放式“替我经营业务”更容易落地。

不适合的任务常见于目标模糊、动作不可逆、凭据治理薄弱或没有可靠验收方法的场景。“自动处理所有客户退款”不是可部署规格；“读取订单记录，检查四项明确政策条件，生成建议，并由员工批准退款”才有机会成为可测试流程。

## 一套更安全的设置路径

### 1. 先写任务契约

明确允许的输入、工具、输出工件、完成条件与停止条件。还要写清证据冲突、来源缺失或工具异常时如何退出，而不是让 Agent 自行猜测。

### 2. 把权限拆成读取、起草与执行

使用范围最小的专用服务凭据。删除、付款、发布、权限变更和外部沟通应保留显式人工批准，不要因为运行时受托管就跳过业务门禁。

### 3. 让状态可以检查

保留来源、工具调用、中间工件、审批记录与最终结果。持久会话只有在操作者能理解它、接管它、恢复它时才有价值。

### 4. 专门测试恢复能力

主动中断会话、撤销凭据、返回格式错误的工具结果、重复事件，并在运行中修改上游记录。检查 Agent 是否安全停止，以及恢复时是否会重复发送、写入或付款。

### 5. 分阶段开放生产权限

先回放历史案例，再以影子模式运行但不执行动作，最后才开放低风险写入并保留审批。只有当团队掌握错误类型和回滚路径后，才扩大范围。

## 如何评估一次试点

使用固定案例集，将 Agent 与现有流程对比。完成率远远不够：

| 指标 | 要回答的问题 |
|---|---|
| 正确率 | 输出是否满足书面验收标准？ |
| 证据质量 | 重要事实和决策能否追溯？ |
| 人工介入率 | 有多少运行需要人来救场？ |
| 越权尝试率 | 是否尝试了策略之外的动作？ |
| 恢复质量 | 中断后能否恢复且不产生重复副作用？ |
| 成本与时延 | 在预计规模下是否经济、及时？ |

失败还应按原因分类：输入问题、上下文缺失、工具选择错误、工具故障、权限问题、推理错误或复核规则不足。并非每类问题都能通过换模型解决。

## 上线前必须确定的安全边界

每接入一个系统，潜在影响范围都会扩大。上线评审至少应回答：

- 邮件、文档、工单或网页中的不可信内容能否影响 Agent？
- 哪些工具可以发送、发布、删除、购买或修改权限？
- 密钥会暴露给模型或 sandbox，还是只由受控工具代为使用？
- 不同租户或会话能否互相读取状态？
- 写操作是否幂等，出现错误后能否回滚？
- 运行停滞或越过风险阈值时，由谁收到告警并接管？

托管运行时不会消除提示注入、受污染来源与过度授权。审批和事故响应仍由构建这项业务能力的团队负责。

## 最后的选型结论

Claude Managed Agents 可以缩短从 Agent 原型到可运营服务的路径，因为持久会话、harness 执行、sandbox 与追踪不必全部自建。但真正决定服务是否可信的工作仍然存在：收窄任务、设计权限、建立评估集、设置人工门禁与验证恢复。

如果你的问题更具体，是一人公司如何划定委派范围，可以继续阅读[一人公司使用 Claude 托管 Agent 的决策指南](/zh/blog/claude-managed-agents-one-person-company)，把本文的架构边界落到更窄的经营场景。

当团队要构建程序化 Agent 服务，并希望 Anthropic 承担大部分运行层时，可以评估 Managed Agents；当需求是让一个人直接委派文件或代码任务，应优先看 Cowork 或 Claude Code；当工作只是即时问答与起草，普通对话通常更简单。
