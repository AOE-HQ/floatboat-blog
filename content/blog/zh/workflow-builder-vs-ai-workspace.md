工作流构建器与 AI 工作区都能让模型连接业务工具，但两者围绕不同控制点组织工作。

工作流构建器从流程开始：触发器、明确步骤、条件、数据映射与输出。AI 工作区从一组正在进行的工作开始：文件、对话、项目、连接知识，以及可以随时改变方向的人。

真正的区别不是“自动化还是 AI”。现代构建器包含 Agent 节点，现代工作区也包含触发器和动作。应该问的是：**权威状态存在哪里，下一步由谁决定。**

## 一张表看清边界

| 维度 | 工作流构建器 | AI 工作区 |
|---|---|---|
| 基本单元 | 一条 workflow 或一次 run | 一个项目、对话或一组工件 |
| 最适合的任务 | 可重复、事件驱动、适合 schema | 探索型、工件密集、方向会变 |
| 下一步控制 | 预设图、规则或受限 Agent 节点 | 模型与用户在执行中协作 |
| 上下文 | 每一步映射字段与检索数据 | 文件、历史、选定来源、当前工件 |
| 状态 | 执行变量、队列、运行历史 | 项目上下文、草稿、文件、对话历史 |
| 输出 | 更新记录、通知、API 动作、结构化工件 | 分析、文档、计划、代码或已复核工件 |
| 人的角色 | 设计流程并处理异常 | 指挥工作并复核中间结果 |
| 扩展目标 | 大量相似运行 | 数量较少但变化更大的知识任务 |

工作流构建器可以包含 Agent，工作区也可以触发 workflow。混合形态不会消除边界：仍需确定哪一层拥有业务流程，哪一层拥有工作上下文。

## 工作流构建器擅长什么

当一个事件需要反复产生可预测的运营结果时，工作流构建器更合适。常见组件包括触发器、连接器、过滤器、分支、schema、重试、调度、审批与执行日志。AI 可以在边界明确的步骤中分类非结构化输入，或从获准工具中选择。

典型任务：

- 校验新线索、补充获准字段、路由并创建 CRM 任务；
- 从发票提取字段、执行确定性检查、把异常交给人复核；
- 从会议转写生成任务草稿，经批准后才创建任务；
- 定时收集数据并发布结构化内部报告。

Make 当前的 [AI Agents 页面](https://www.make.com/en/ai-agents)强调 Agent 位于可视化自动化画布内、工具可复用、决策可查看。这不是由一家厂商定义品类，而是说明 Agent 判断可以被放进受控 workflow。

当每次流程都不同、输入主要是非结构化文件、成功依赖持续解释，或用户需要反复重塑输出后才知道“完成”是什么时，构建器不再合适。

## AI 工作区擅长什么

当工作及其证据需要放在一起持续查看时，AI 工作区更合适。用户带入文件、选择来源、给出指令、审阅草稿，并随理解变化调整方向。

典型任务：

- 比较一批合同并迭代形成风险备忘录；
- 使用网页来源、内部笔记与不断变化的问题开展市场调研；
- 在调整定位、证据和交付物的同时起草发布计划；
- 检查文件、测试和中间 diff，对代码库做重构。

Notion 官方 [Agent 文档](https://www.notion.com/help/notion-agent)描述了 Agent 如何使用当前页面、选定工作区来源、连接应用、文件、指令与 skills。Google 也明确说明，Gemini 对 Workspace 数据的访问仍受管理员与内容所有者权限限制。这些都是工作区的关键属性：上下文必须带来源并受权限约束，才真正有用。

当同一操作需要高吞吐、严格 schema、可预测重试、队列语义、事务保证或无人值守 SLA 时，工作区通常不是合适的执行层。

## 上下文与状态：最重要的区别

在构建器中，上下文通常为每个节点或 Agent 调用明确组装；状态是机器运行，包括触发数据、变量、工具结果、重试次数、审批状态和副作用 ID。

在工作区中，上下文是人与模型当前使用的材料：项目文件、选定消息、指令、草稿与对话历史。状态还包括让下一轮迭代可以理解的工件与决策演变。

两类产品都不会“记住一切”。构建器会丢失没有映射或保存的数据；工作区可能检索错来源、遗漏文件或超出上下文限制。两边都应要求来源标识、版本与时间戳。

实用判断：需要机器可重放状态时用构建器；需要人可理解、可编辑状态时用工作区；两种需求同时存在时组合使用。

## 权限与审批

连接器是授权边界，不只是便利功能。

工作流构建器常使用服务凭据。优点是每个动作可以限制、校验、审批与记录；风险是一个长期凭据可能静默支撑大量流程。

工作区 Agent 可能沿用用户权限，也可能拥有独立身份。两者不能混为一谈。Notion 当前文档就区分了沿用用户权限的个人 Agent 与拥有独立资源权限的 Custom Agents。分享后一种 Agent，可能让使用者通过它接触 Agent 本身可访问的内容。

两类产品都应：

- 分开读取、草稿、可逆写入与高影响写入；
- 发送、发布、付款、删除或改权限前要求审批；
- 审批时显示拟执行动作与依据；
- 使用最小权限凭据；
- 清理无人负责的 Agent、离职所有者和闲置连接器；
- 将外部文档与消息视作不可信输入。

## 可观测性与恢复

构建器应展示运行输入、每一步、映射值、工具参数、输出、错误、重试、耗时、成本与副作用 ID。恢复需要幂等、checkpoint、重试策略、dead-letter 路径和重放控制。

工作区应展示选定来源、文件版本、指令、模型/工具动作、中间工件、审批与最终编辑。恢复意味着保存草稿、知道使用了哪些来源，并允许人从断点继续或创建分支。

只有“活动历史”还不够。对两个产品执行相同故障演练：

- 撤销连接器；
- 返回格式错误的数据；
- 重复触发事件；
- 读取后修改来源；
- 分别在写入前后中断；
- 移除原始所有者；
- 请求策略之外的动作。

更好的产品，是第二位操作者能够解释故障并恢复，而且不会重复有害动作的那一个。

## 成本与运营模型

工作流构建器成本通常随 operations、executions、高级连接器、队列容量、存储与模型调用增长，还要加上维护映射和调查失败的人力。

AI 工作区成本通常随 seats、套餐、模型或 credits 用量、存储、连接器资格与人工复核时间增长。Notion 当前文档就分别说明了部分高级模型的使用额度与管理员控制；具体价格随时可能变化，应在购买时核对。

比较“每个被接受结果的成本”，不要只看单次自动化或单条 AI 消息。包括：

- 搭建与入职时间；
- 人工复核与修正；
- 失败与重试；
- 连接器或模型变化；
- 安全与合规评审；
- 离开平台时的导出与重建。

## 锁定与迁移

两类产品都会产生锁定，但形态不同。

工作流构建器的价值存在专有流程图、连接器映射、凭据、执行历史与平台表达式中。导出 JSON 可能保留结构，却无法复刻托管连接器或运行时行为。

AI 工作区的价值存在页面、文件、权限、链接、评论、数据库 schema、Agent 指令与对话历史中。文件导出未必保留关系、访问规则、引用或 Agent 配置。

尽量把以下资产放在产品之外：

- 任务契约与验收标准；
- 提示词与指令版本；
- 工具 schema 与权限矩阵；
- 评估案例；
- 权威来源 ID；
- 导出计划与恢复测试；
- 运行或工件索引；
- 所有者与离职处理流程。

“有 Export 按钮”不等于可迁移。可迁移意味着能在别处重建有用行为与证据。

## 什么时候组合使用

好的混合架构让探索留在工作区，让稳定重复进入构建器。

例如，团队先在工作区调研客户并形成资格判断规则。规则稳定后，构建器接收每条新 CRM 记录，收集获准数据，执行确定性检查，用受限模型步骤分类，再把不确定案例送回工作区复核。

交接必须有契约：

- 结构化输入输出 schema；
- 稳定来源链接；
- 置信度或异常原因；
- 审批责任人；
- 幂等键；
- 能改进下一版本的反馈字段。

没有契约，“集成”只是在两个黑箱之间复制上下文。

## 两周选型试点

用一个有代表性的任务与同一测试集比较两种方案。

### 1. 定义工作

写明触发、输入、允许来源、允许动作、预期工件、审批、停止条件与成功标准。

### 2. 包含正常与对抗案例

测试字段缺失、来源冲突、重复触发、文档提示注入、连接器不可用、权限变化与运行中断。

### 3. 构建最小版本

在构建器中，把确定性步骤放在模型之外；在工作区中，固定必需来源并要求引用。

### 4. 运行影子模式

不允许外部写入，与现有人工流程比较。

### 5. 只开放一个可逆动作

例如创建草稿、添加标签或写入测试数据库；高影响动作继续要求审批。

### 6. 衡量运营而不是演示效果

跟踪合格结果、修正时间、介入率、越权尝试、恢复时间、时延、完整成本，以及第二位操作者理解一次运行所需时间。

## 选型矩阵

| 工作特征 | 优先起点 |
|---|---|
| 事件驱动、重复、结构化、高数量 | 工作流构建器 |
| 探索型、文件密集、依赖判断、经常改方向 | AI 工作区 |
| 基本稳定，只有一步需要分类或起草 | workflow + 受限 AI 步骤 |
| 当前探索，但未来可能稳定重复 | 先工作区，再抽取 workflow |
| 重复但异常复杂 | 构建器 + 工作区异常队列 |
| 产品关键且需要自定义保证 | 代码或托管运行时，可同时提供两种界面 |

## 最终建议

组织已经理解流程，并希望反复执行时，选择工作流构建器；工作本身仍在被理解，人需要持续掌控上下文、证据与工件时，选择 AI 工作区。

不要让任何一类产品掩盖另一类能力的缺失：工作区不是事务引擎，构建器也不能替代探索型判断。更稳健的架构常让工作先在工作区成熟，再把稳定部分提升为受治理的 workflow。
