**TL;DR**
  * **Floatboat Flow Mode**是 Floatboat 里一个语音优先的写作层：语音、手动编辑和 Agent 协作发生在**同一份文档**里——不打断你的思路。

  * **边说边改**：实时**AI 语音口述**持续流进草稿的同时，你选中一句话，让 Agent 就地润色。

  * **批量批注**：在长文档里圈出几个位置、用语音描述每处改动，把整捆一次性交给 Agent。

  * **会议实时产出**：对话还在进行时，讨论就排成笔记，并可能变成带负责人的清单——不必等散会后有人去开一个单独的**AI 会议纪要**工具。

  * **带 diff 的版本历史**：每一次语音与 Agent 编辑都被记录；做实验时能对比版本、安全回滚。

**Floatboat Flow Mode**是为文档工作而生的**AI 语音口述**：你留在草稿里，Agent 守在你身边，四周的日历驱动 workspace 照常处理会前准备、截止日和跟进。

## 1\. Flow Mode 上线了：表达不再等工具

如果你靠写作为生——是起草发布帖的独立创始人、在打磨客户方案的顾问、或把会议发言变成计划的运营人——你早就懂那种摩擦。**语音转文字**把话变成字比打字快，但多数工具把听写当成一种独立模式：停下说话、改段落、把一段复制进聊天框、把改好的粘回来、再来一遍。**AI 会议纪要**应用能把会议录得好，可交付物往往在会**之后**才来，躺在另一个标签页里，和你正想写完的那份文档毫无关联。

**Floatboat Flow Mode**是我们对这个割裂的回应。它不是独立的听写工具，也不是旁挂一个会后的总结器。它是 [Floatboat](</>) 内部的一层表达能力：**语音输入、编辑、Agent 改写、会议捕捉、版本控制**共用同一副界面——也就是你真正想交付的那份文档。

这个目标又简单又难：**别打断你的流**。你说，草稿长。你要精确时，才碰键盘。Agent 在你选中的片段上干活，而不是在一条脱离文档的聊天线程里。会议还在开，下一步的框架就已经可以摆在桌面上了。

## 2\. 问题所在：工具打断句子，而不是反过来

大多数写作组合假设你会为了寻求帮助而**切换上下文**。听写应用——包括 <a href="<https://wisprflow.ai/>" rel="nofollow noopener">Wispr Flow</a> 这类出色的系统级工具——擅长把语音转成干净文字，**你的光标在哪就落到哪**。这对邮件、Slack 和短字段确实有用。但它们通常不优化的场景是**长文合写**：一份在二十分钟口述里不断演化的草稿、中途的编辑、以及对同一文件不同段落的多次 Agent 打磨。

会议 AI 有同样的缺口。成熟的**AI 会议记录工具**，如 <a href="<https://otter.ai/>" rel="nofollow noopener">Otter</a> 和 Fireflies，强在转写、搜索和会后总结。它们的重心是**录音生命周期**，而不是一份必须在对话_进行中_就绪的工作文档。如果你的任务是散会时就带着一份干系人可以回应的行动清单——而不是一份之后再去处理的逐字稿——那重心还是摆错了。

聊天式写作助手会补上第三种打断。把一段贴进 Claude 或 ChatGPT，拿回一版改写，再贴回去。智能是真的，但**文档不是运行时**。对已经要在日历准备、客户电话和发稿之间辗转的单人创业者来说，这条多余的回路正是心气耗尽的地方。

我们围绕另一个重心打造了 Flow Mode：**文档即工作区**，语音是主要输入，Agent 是同一份文件里的协作者——这与 Floatboat 更大的**Calendar-Driven**故事一致：工作由你日程上的事触发，而不是由你「记得打开」的某个聊天窗口触发。这不是说对话式的表面一无是处——多人协作的「人 + agent」线程本来就该待在 [FloatIM 这样的 agent 原生消息网络](/zh/blog/introducing-floatim) 里——而是说草稿不是线程：合写需要以文档本身为运行时。范式的深入对比见 Calendar-Driven AI vs Chat-Based AI。

## 3\. Floatboat Flow Mode 做什么（大白话版）

Flow Mode 以四项能力交付，正好映照人们真实写作和开会的方式。它们可以单独用；合起来，覆盖从第一句口述草稿到安全改稿的整条路径。

### 3.1 边说边改

传统**语音打字**常常把你锁进「先录后改」的节奏：录完一整段，再编辑。Flow Mode 让**实时转写**持续流进文档，而你随时可以直接改词。一句话差不多了但还差点意思时，选中它、把那段交给 Agent——不用中断整个听写会话。

实际观感是：你说着话，一大段想法落进文档；一个短语快速手改；然后对需要打磨的那一行做一次定向 Agent 改写。Agent 面板体现的转变是「被动捕捉 → 主动协作」，段落其余部分仍归你。如果你用过 Aqua Voice 的 Edit Mode 那种基于选区的语音编辑，这种交互会似曾相识——但在这里它是**持久化 Agent workspace**的原生能力，而不只是一层跨应用键盘层。

这是我们在乎的核心**AI 语音口述**差异：听写不是终点，而是流进一份由你和 Agent 共同拥有的文档的持续原料。

### 3.2 长文档的批量批注

短提示词在你需要它的时候都好用，直到不够用。一篇品牌故事、一份政策草稿或一份多章节方案，往往需要**许多小改**——第四行收紧语气、第十二行换掉一个含糊的形容词、第十八行加一个数字。在串行聊天里逐条描述每处修改很烦人；在 PDF 上做标注、指望有人去照做更糟。

Flow Mode 让你**选中一个短语**、用语音描述改动，然后在录音继续的同时把这条备注停进一个「批注捆」。语音备注先落进缓冲区；由你决定何时插入，这样你不会在句子中途丢掉一条半成形的指令。当批注捆备齐——三处位置、三个意图——你把整包一次性发给 Agent。每个「片」都带着自己的**行锚点**，所以改写落在你本来要的位置，而不是模型猜的位置。

对任何在 Floatboat 里编辑长 Markdown 或简报的人来说，这就是「跟聊天框聊这份文档」和「带着结构化意图_对着_文档说话」的差别。

### 3.3 会议实时产出——而不只是会后笔记

Flow Mode 的会议视图会在对话展开时逐人逐行记录谁说了什么。光这一点就省了手忙脚乱的时间；更深的一步是**会议进行中就能编辑早先的行**。有人修改了某条行动的措辞，你更新实时那一行，捕捉不中断。

当讨论推进得足够远，你把最新上下文推给 Agent。产出不是一整面逐字稿墙，而是一份**工作计划**：一个标题、可勾选的条目、以及挂在上面的负责人。会议可能还在进行，计划草稿就已经出现。这补上了 Floatboat 既有的 AI 会议准备管线（会前上下文）和 AI 跟进自动化（结构化会后下一步）——Flow Mode 填的是**会中**那段，而记录工具很少为这段优化。

我们不是说要去替代每支团队专用的会议机器人；Otter 之类的工具在生态广度和会议搜索上仍然更强。Flow Mode 是给那些想要**文档里有交付物**的运营人做的——而不只是一份别处可搜索的录音。

### 3.4 大胆实验时，有版本历史兜底

语音和 Agent 的编辑会让草稿动得很快——这正是目的——而动得快会让人犹豫，除非回滚很容易。Flow Mode 记录**版本历史**，带可读的标签与时间戳。打开一个较早的修订，看它和当前文本的**diff**，如果某次 Agent 打磨过了头，一步就能回退。

这张安全网对公开起草的独立创始人很重要：你可以在开头段落上试一次激进的改写、对比、然后退回去——不必在「撤销」或散落的聊天线程里考古。

## 4\. Flow Mode 在 Floatboat workspace 里的位置

Floatboat 仍是**那个从日历驱动工作的主动式 Agent OS**——Agent 会前准备、按截止日执行、会后跟进。Flow Mode 不替代这台引擎；它强化了那些产出的**表达面**。

想一个典型的客户日：日历触发一份会前简报（准备管线）；你上线通话，用 Flow Mode 的实时计划捕捉决策；时段结束后，跟进草稿和任务沿着既有的自动化故事流转（跟进管线）。语音帮你把备忘录说出来；批量批注把长文档清理干净；版本让实验可逆。

如果你把研究存在 Obsidian 或本地 markdown 里，Flow Mode 也自然搭配「如何把 Obsidian 和 AI agent 一起用」那套工作流——口述一版草稿、就地打磨、把上下文留在你控制的文件里，而不是留在一场用完即弃的聊天会话里。

Flow Mode 是 Mac 和 Windows 上 Floatboat 里的**桌面 workspace**功能——和 Combo Skills、多模型路由、事件级 Agent workspace 同处一个环境：你口述的这份草稿旁边，就可以是一个正在跑[每周 TikTok Shop 选品调研](/zh/blog/automate-tiktok-shop-research-fastmoss-floatboat)的 agent——一台桌面、多份 agent 工作，不必在标签页之间来回搬运。具体可用性随版本而变；以线上应用和发布说明为准。

## 5\. 一个快速场景：从口述草稿到定稿计划

想象一个产品发布周。周一早上你打开一份发布备忘录，打开 Flow Mode。接下来的十五分钟，你口述定位——不需要先有提纲——章节随说话浮现。你选中标题那句，让 Agent 给一个更利落的钩子；只有那一段变了。

周二你给一篇更长的故事做品牌评审。你高亮三个别扭的短语，把三处修改口述进批注捆——不打断房间里正在录的讨论——逐条插入备注，把整批一次发给 Agent。周三的客户工作坊逐行被捕捉；会中你改一条行动措辞；挂断前你生成一份带负责人的清单。周四你把今天的开头和周一版本对比，留下更好的钩子，把一段跑得过于口语的段落回退。

自始至终，你都没有把文档导出到聊天框，也没有等到周五才去「处理录音」。这就是 Flow Mode 为之设计的工作流。

## 结论

**Floatboat Flow Mode**把**AI 语音口述**当作合写的起点——而不是通往原始逐字稿的捷径。如果你的瓶颈是在说话、打字、聊天和会议工具之间来回切换，解法不是更响的提示词，而是一条尊重节奏的单一文档流。尊重节奏也包括文档之外的小摩擦——按下录音键之前那些找窗口、切应用的动作，交给 [Raycast 风格的 Windows 启动器](/zh/blog/raycast-for-windows-floatboat) 去做就好。

在最新版 Floatboat 里试试 Flow Mode，入口 [floatboat.ai](</>)。如果你想先对比范式，去读 Calendar-Driven AI vs Chat-Based AI；如果你的周被会议占满，把这发布和博客上已有的会议准备、跟进指南配起来用。
