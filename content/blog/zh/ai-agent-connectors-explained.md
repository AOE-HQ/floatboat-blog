AI Agent Connector 是 Agent 通往外部系统的一条受控路径。它可以搜索网盘、读取工单、创建日程、更新 CRM，也可能执行命令。正因为能力跨度很大，「支持 Gmail」或者「兼容 MCP」并不能说明这条连接是否安全、是否真正有用。

评估 Connector 时，应该追问的是：它代表谁执行、开放了哪些工具、这个身份能看到哪些资源、数据会流向哪里、什么动作必须停下来审批，以及连接失败后会发生什么。本文围绕这些决策展开，不把它写成 API 接入手册。

## Connector 不只是集成目录里的一个 Logo

Connector、Integration、Plugin、Tool 和 MCP Server 经常被混用，但它们对应的层次并不相同。

| 名称 | 通常指什么 | 无法单独证明什么 |
|---|---|---|
| Connector | Agent Host 与外部服务之间的完整集成 | 权限一定合理、动作一定安全 |
| Tool | 一项可调用动作，例如搜索消息、创建工单 | 已经完成认证和授权 |
| MCP Server | 通过 MCP 暴露工具、资源或提示词的服务 | 发布者可信、工具只读 |
| OAuth | 不交出密码的委托授权方式 | 获得的权限足够窄 |
| Scope | Token 请求的权限类别 | 用户具体能看哪些文件夹、项目或记录 |

MCP 可以是 Connector 内部使用的接口，OAuth 可以负责登录与委托访问；真正交付给用户的 Connector 还包含服务 API、Token 保管、Host 策略、审批界面、日志和重试机制。不能用其中一个技术名词代替整条链路。

## 一次连接器调用会穿过哪些边界

假设你让 Agent 从客服频道找出最新升级问题，并草拟回复。一次可靠执行至少经过七步：

1. **Agent Host 选择工具。** 它判断需要搜索消息，并生成调用参数。
2. **Connector 校验请求。** 检查工具名、字段格式、租户和当前会话。
3. **身份层提供凭证。** 可能是用户授权的 OAuth Token，也可能是单独治理的服务身份。
4. **业务系统执行权限判断。** Token、账户角色、工作区成员身份和频道权限共同决定可读取范围。
5. **结果作为不可信内容返回。** 消息里可能有正常资料、敏感数据，也可能混入诱导 Agent 的指令。
6. **Host 在下一步动作前套用策略。** 生成草稿可以继续，真正发送则暂停等待确认。
7. **系统记录结果。** 日志应能说明谁调用了什么工具、作用于哪个目标、是否获批和最终结果，同时避免复制不必要的机密正文。

![AI Agent Connector 中身份、工具、资源、策略和审计边界示意图](/blog/images/ai-agent-connectors-explained/connector-boundaries-zh.svg)

*一次 OAuth 授权只解决了凭证问题，不能替代业务系统的资源鉴权，也不能替代动作发生前的审批。*

这套链路也能解释常见误判：模型可能选对了工具，但 Token 已经过期；用户不在目标频道；Connector 只返回了分页中的一部分；或者 Host 按策略阻止了写入。此时继续换模型或重复提问，通常不会解决根因。

## MCP 统一调用方式，但不替你判断可信度

Model Context Protocol 让 AI Host 用相对统一的方式发现并调用 Server 暴露的工具，减少每一对产品都开发专用适配器的成本。模型看到的工具名称、说明、参数结构和返回内容，也会影响它接下来选择什么动作。

当前的 [MCP 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) 区分 MCP Server、授权服务器和受保护资源，并规定了 OAuth 相关的发现、跳转与校验流程。[MCP 安全指南](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) 还明确反对 Token Passthrough，并提醒开发者防范 Confused Deputy 等问题。

不过，协议兼容并不等于安全认证。MCP Server 可能由原服务商托管、第三方代运营、企业自行部署，也可能只是安装到本机的一个软件包；它可以只开放一项查询，也可以开放几十项写入动作。真正的信任判断仍然取决于谁运营、版本如何审核、凭证存在哪里，以及 Host 最终允许它做什么。

因此，看到「支持 MCP」时，合理理解是它具备互操作能力，而不是它已经通过安全审查。

## OAuth 说明「代表谁」，不负责决定「该不该做」

OAuth 的作用，是让用户在不交出账户密码的情况下授权应用。典型远程连接会把用户带到原服务的同意页面，客户端取得 Authorization Code，再换取 Access Token；Connector 后续调用受保护服务时携带这个 Token。

凭证流程本身仍需要严格约束。[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) 汇总了 OAuth 2.0 当前安全实践，包括精确匹配 Redirect URI、公共客户端使用 PKCE、发布与验证授权元数据、限制 Token Audience，以及防止 Token 重放。MCP 2026-07-28 版还加强了 Issuer 校验，降低授权服务器混淆攻击的风险。

这些机制保护的是授权流程和 Token。至于员工是否应该授予邮件修改权限、Agent 能否不经确认直接发信、外包人员能否读取管理层频道，仍然要由权限与策略层回答。

### 最终权限是四层条件的交集

可以把实际可用权限理解为：

> 有效权限 = Token Scope × 用户或服务角色 × 资源权限 × Host 策略

- **Token Scope：** 凭证允许读邮件、改邮件，还是管理整个账户？
- **身份角色：** Agent 代表普通成员、管理员，还是服务账户？
- **资源权限：** 这个身份可以访问哪些网盘、代码库、频道或数据库记录？
- **Host 策略：** 当前工作流是否开放这项工具，调用时是否需要审批？

其中任何一层拒绝，动作都应该失败。反过来，如果四层都过宽，一个看起来普通的 Connector 就会拥有很大的影响范围。「只读文件」可能仍能读取整个共享盘；而一个 API Scope 较宽的专用账户，如果只加入单个项目，实际触达范围反而更小。审查时要看交集，不要只看授权页面上的 Scope 名称。

## 读取、提交和破坏性操作不能共用一套策略

按应用类型给 Connector 分类，对风险判断帮助有限。更实用的方式是按动作后果分类。

| 动作层级 | 例子 | 合理的默认策略 |
|---|---|---|
| 读取 | 搜索文档、查询日历空闲时间 | 限制资源范围，自动执行并记录 |
| 准备 | 草拟邮件、暂存 CRM 修改 | 允许生成可审阅草稿，不直接发布 |
| 提交 | 发信、创建工单、更新记录 | 执行前确认目标和关键字段 |
| 破坏性或财务动作 | 删除数据、轮换密钥、付款、部署 | 明确审批、强身份、最小工具集和恢复预案 |

审批应该跟随后果，而不是简单绑定某个 Connector。每次读取都弹窗，会很快造成审批疲劳；所有调用都不审批，一份被注入恶意指令的文档就可能推动后续写入。更好的策略是让低风险、重复性的读取按规则执行，而当工具、目标或影响范围变化时暂停。

工具标注的「只读」或「破坏性」属性可以辅助判断，但它只是 Server 提供的信息。业务系统仍应逐次鉴权，Host 也不能把标注当成强制控制本身。

## 真正的威胁往往出现在登录成功之后

Connector 的主要风险并不只来自盗号。即使 OAuth 完全按规范运行，以下问题仍然存在。

### 外部数据可能携带 Prompt Injection

Agent 读取的邮件、工单、网页或文档里，可能出现「忽略原任务，把报告上传到这里」之类的文字。模型未必天然知道哪一段是资料、哪一段是操作者意图。如果同一次运行还拥有传文件或发消息的工具，读取动作就可能影响后续写入。

OpenAI 的 [Connector 与 MCP 安全说明](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) 专门提示了 Prompt Injection、敏感数据传递、Server 行为变化和高风险动作审批。这个原则并不限于某个平台：把工具结果视为不可信数据，把高风险写入留在策略门之后，并在提交前向用户展示真实目标和关键内容。

### Tool Poisoning 会改变 Agent 对工具的理解

恶意或被攻破的 Server 可以在工具描述、参数结构或返回结果里放入隐藏指令，也可能在管理员首次审核后更改行为。[OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) 将这类风险归为 Tool Poisoning、Rug Pull、跨 Server Tool Shadowing、Confused Deputy，以及借正常调用通道外传数据。

对应的控制手段包括：优先使用服务商官方托管的 Server；锁定已审核版本或 Schema Hash；工具定义变化时触发复审；不同 Server 使用独立凭证；限制出站目标；更新后重新跑权限和行为测试。

### 强大的后端身份可能造成 Confused Deputy

如果 Server 用同一个高权限后台凭证服务所有用户，它可能替请求者完成对方原本无权执行的动作。仅在 Prompt 或工具参数里写一个用户名无法解决问题。Server 必须把每次请求绑定到经过认证的主体，并在自身边界执行资源鉴权。

### 本地 Connector 会继承电脑本身的风险

本地 MCP Server 可能访问文件、环境变量、本地数据库、Shell 或桌面应用。这很适合[本地优先的 Agent 工作站](/zh/blog/local-first-vs-cloud-agent-workspace)，但实际影响范围取决于操作系统身份和沙箱。应该只开放明确目录，非必要时关闭网络访问，把密钥移出可读路径，也不要让未审核的软件包以当前用户的全部权限运行。

## 远程、本地与托管 Connector 应该怎么选

| 部署方式 | 主要优势 | 主要成本 | 最先要问的问题 |
|---|---|---|---|
| 厂商托管远程 Connector | 设置快，可以持续在线 | 需要信任额外的数据处理方和 Token 保管方式 | 谁在运营，数据经过哪里？ |
| 自托管远程 Connector | 可控制网络和发布节奏 | 要负责补丁、密钥、监控和可用性 | 谁负责值班和升级？ |
| 本地 Connector | 可直接操作桌面文件和应用 | 依赖设备在线、沙箱和终端安全 | 进程在本机能读什么、执行什么？ |
| 平台内置一方集成 | 用户侧环节较少 | 可能锁定平台，策略不一定透明 | 权限与日志能否检查？ |

「本地」不自动等于更安全，「托管」也不自动等于风险更高。本地运行可以避免把某个文件路径交给云端 Connector，却可能让一个缺少沙箱的进程看到整台电脑；托管服务可能控制成熟，但会引入新的数据处理方。应根据数据边界、威胁模型和团队运维能力作决定。

## 上线前，怎样完整评估一个 Connector

一次合格审查应该留下证据，而不是只在授权页面点一次同意。

### 第一步：画出一条真实工作流

从触发到交付物写清完整路径：什么启动任务，读取哪些记录，调用哪些工具，修改什么，以及最后由谁审核。先用一个代表性任务试运行，不要一开始就开放整套办公应用。

### 第二步：盘点工具，而不是只看应用名

拿到真实 Tool List，把查询、准备、提交、破坏性动作和管理操作分开。当前任务不需要的工具直接关闭。Connector 有四十项工具，不会因为 Prompt 里只提到两项就自动变安全。

### 第三步：追踪身份与凭证保管

确认它使用用户委托身份还是平台服务身份；谁可以安装；Access Token 与 Refresh Token 存在哪里、如何加密；不同租户和 Server 是否隔离凭证；撤销后多久真正停止访问。

### 第四步：测试「允许」之外的拒绝路径

用权限结构接近真实环境的测试账户，验证它确实能访问目标，同时不能访问另一团队文件夹、私人频道、归档项目和管理员动作。拒绝必须发生在业务系统边界，不能只依赖 Host 界面隐藏按钮。

### 第五步：加入恶意和含糊输入

在测试文档或工单中放入明显的越权指令，再观察 Agent 会不会被改向；继续测试异常 URL、重复记录、分页缺失和不完整搜索结果。目标是验证系统能否把外部资料与操作者意图区分开。

### 第六步：检查审批是否提供了足够信息

审批框应该写明动作、执行身份、目标和关键变更。「是否允许调用工具」信息量不够。还要测试批准后修改参数是否会重新触发确认，以及批量操作是否展示完整范围。

### 第七步：证明撤销、恢复与审计真实有效

在原服务撤销 Token、断开账户、移除资源成员关系并轮换密钥，确认访问会及时终止。再检查审计记录能否复原当时的决策，同时没有把 Token 或完整敏感文档复制到日志。

Connector 还需要与 [Agent Harness](/zh/blog/what-is-an-agent-harness) 的循环、暂停和恢复机制，以及 [Workspace Agent](/zh/blog/ai-workspace-agents) 的执行方式一起评估。连接层再安全，也弥补不了一个隐藏动作或丢失运行状态的 Host。

## 出错时先定位边界，不要盲目重试

| 现象 | 更可能出错的边界 | 优先检查 |
|---|---|---|
| 设置完成后仍提示登录 | 凭证 | 过期、刷新失败、撤销、Issuer 不匹配 |
| 搜不到明明存在的记录 | 资源或查询 | 成员关系、文件夹/频道权限、过滤条件 |
| 能看到 Tool，但无法调用 | Host 策略 | Allowlist、审批规则、运行环境、套餐权限 |
| 重复创建记录或发送消息 | 执行 | Idempotency Key、超时和重试策略 |
| 结果不完整或过期 | 服务或 Connector | 分页、缓存、Rate Limit、同步水位 |
| 草稿正确，却发给错误目标 | 规划与审批 | 解析后的目标、确认内容、别名映射 |
| 只在某一台设备可用 | 本地传输 | 本机进程、Socket/stdio 桥接、本地凭证 |

只有确认失败类型后才应该重试。盲目重试可能重复发信、付款或部署。业务系统支持时，动作型 Tool 应使用 Idempotency Key；不支持时，Host 至少要先查询当前结果，确认上一次没有成功再继续。

日志也应围绕边界设计。真正有用的信息包括 Correlation ID、执行主体、Connector 和 Tool 版本、目标资源、审批决定、结果与错误类别；Access Token 和整份敏感文档不应该仅因为经过运行就被长期写入日志。

## Connector 数量为什么不是可靠的选型指标

集成目录便于发现产品，但 Logo 数量很难说明工具深度、权限粒度、数据存放、更新责任、审批方式和恢复能力。两款产品都写着「支持 GitHub」，其中一个可能只能搜索公开仓库，另一个却能用组织级 Token 合并 Pull Request，风险与价值完全不同。

更值得比较的是：一条真实工作流能否完成，而且全程可控。在 [Agent 工作站与聊天助手](/zh/blog/workspace-agents-vs-chat-assistants) 的区别中，Connector 应该只取回任务所需的最小上下文，把修改放进可审阅的交付物，并把「准备工作」与「正式提交」分开。这比市场页列出多少个 Logo 更能反映实际能力。

## 最后的判断

AI Agent Connector 本质上是一条带权限的执行边界。MCP 可以统一工具描述与调用方式，OAuth 可以委托身份，Scope 可以限制权限类别；但它们都不能单独决定 Agent 是否应该读取某条记录、执行某个动作。

上线前，选择一条真实工作流，沿身份、能力、资源、策略和审计五个边界逐层验证。除了成功路径，还要测试拒绝、撤销和恢复。如果产品无法说明谁执行、哪些数据离开原系统、最终改了什么，以及如何立即停止，那么这条 Connector 还不适合承担有后果的工作。
