## TL;DR

- **AI 输出选 HTML 还是 Markdown，选的是「这份输出的活」，不是抽象意义上哪个格式更强：**输出会被编辑、进版本管理、或交给另一台机器消费时，Markdown 仍是正确默认；而当一个人需要扫读、对比、并据此行动的那一刻，HTML 就值回它额外的重量。
- 速记版：内部笔记与 Agent 间交接归 Markdown；给人看的报告、原型、可分享成果归 HTML。第 2 节有完整速查表，还给「两种都要的混合周」留了一行。
- 按顺序问四个问题，绝大多数情况就有了答案：谁读这份输出、生成之后还会不会改、需不需要视觉结构、会不会被复用或模板化。
- 同样的内容，HTML 的输出 token 通常比 Markdown 贵，视觉结构越重差距越大——而 Markdown 的渲染效果随引擎漂移：GitHub 不等于 Obsidian，也不等于 Notion。
- 契合度比功能重要。站得住的默认做法：Markdown 里起草和迭代，快要给人看时再转换或精修成 HTML。

## 1. 别再问「哪个格式更好」

这个问题现在无处不在——私信、评论、客户电话里都有，而且永远是同一个句式：我现在是不是该让 AI Agent 输出 HTML，而不是 Markdown？2026 年 5 月它变得更响，Anthropic Claude Code 团队的一位工程师提出 HTML 成果物的沟通效果优于 Markdown，并放出一组可运行的示例作证。那场把这个话题推上主流舞台的双格式实验——同一份实施方案用两种格式各生成一次，HTML 版的导航与颜色分级让人真的读到了最后——的完整来龙去脉，我们已经在[「HTML 就是新的 Markdown」争论全记录](/zh/blog/html-is-the-new-markdown)里讲透；本文刻意跳过起源之争，只回答它底下那个操作层面的问题。

答案取决于一个变量：这份输出到底是干什么用的。不是抽象意义上哪个格式「更好」，也不是这个月哪个更时髦。一份你明天要改、周五要进 Git 看 diff、下周要交给另一个 Agent 解析的输出，和一份客户打开一次、读九十秒、然后据此做决定的交付物，要求完全不同。这是两种不同的活，理应配不同的格式——硬要一个格式通吃，要么为没人用的结构付钱，要么发出没人读得下去的东西。

两种失败模式都是真实的，而且都比省下的那点选择成本更贵。内部笔记要 HTML，意味着每次修改都要跟内嵌 CSS 搏斗，每个版本 diff 都是一团读不懂的噪声；客户季度评审要 Markdown，意味着读者面对一墙标题，既没法导航、没法对比、也没法排优先级——而一份难以导航的文档，就是一份被略读然后被遗忘的文档。这篇文章剩下的部分就是教你避开这两种结局：先给决策表，再讲每个格子背后的道理，最后给一套三十秒跑完的四问框架。

## 2. 快速决策表：四个场景、两种格式

进入论证之前，先给速查表。四个场景覆盖了 Agent 在正常一周里产出的大多数内容，每一行的读法都一样——观众加生命周期：谁消费这份输出，生成之后它接着会发生什么。

| 场景 | Markdown | HTML |
|---|---|---|
| 内部笔记（自用、从不外发） | 用它——轻量、可编辑、生成快 | 杀鸡用牛刀：没人要这些结构 |
| Agent 间交接（输出喂给下一个 AI 步骤） | 用它——省 token、易解析 | 白花成本，因为没有观众 |
| 给人看的报告（有人要读并据此行动） | 能用，但视觉结构有限 | 用它——层级、颜色、导航撑起阅读 |
| 可分享的成果（发布、复用、演示） | 难排版；渲染效果随平台漂移 | 用它——自包含、可移植、有视觉 |
| 混合周（先起草、后交付） | Floatboat 桌面工作区与免费网页工具在同一个文件树里处理两种格式——Markdown 里起草，不用换工具就能交付渲染页 | 没有格式锁定：同一工作区双向预览与转换 |

前四行过的是同一道测试。输出的下一站是编辑器、Git diff 或另一台机器，Markdown 就是正确选择；下一站是一个需要看懂并做决定的人，HTML 就自己挣回了成本。第五行性质不同——它存在是因为现实中大多数一周两种输出都会产生，而一个让两种格式并排存在的工作区，免去了你在周一早晨之前就宣誓效忠某一阵营的压力。

关于这张表，有两个诚实的提醒。第一，行分的是场景，不是文件类型：一份只有你自己会读的「报告」，不管标题写什么，它都是内部笔记——按「接下来发生什么」分类，别按文档自称什么分类。第二，边界情况是存在的——一份客户读一次、然后团队改一个季度的评审，就同时是两种活——第 6 节的四问框架就是处理这些的。表给你默认答案；问题给你例外情况。

## 3. Markdown 依然赢的地方：可编辑、进版本管理、给机器读

Markdown 不会消失，这一点值得直说，因为「HTML 是新的 Markdown」这场讨论有时听起来像 Markdown 已经坏了。它没坏。它的优势恰好集中在 Agent 输出度过大部分生命的地方——编辑器里、仓库里、流水线里——而这些地方从来没有要求过更好的排版。

凡是进版本管理的东西都该用 Markdown：README、变更日志、技术规格、CLAUDE.md 上下文文件。原因是 diff 的干净程度。一次 Markdown 修订读起来就是「改了哪些话」——这里加了一行，那里重写了一句；而一次 HTML 修订在标签层翻搅，真正的内容改动淹没在结构噪声里——在 pull request 里审 HTML diff，就像隔着万花筒读一份被红笔批注的法律文件。当一份成果物的活是「住在仓库里、随提交逐代演化」时，最朴素的格式就是赢家。

版本管理的论点还可以延伸成生态论点。构建者会碰到的几乎所有平台都原生解析 .md——GitHub、[Obsidian 式的互链笔记库](/zh/blog/what-is-obsidian-vault)、静态站点生成器、文档流水线——所以 Markdown 输出到哪儿都是开箱即用。而且 Agent 真正需要的词汇表很小：标题、列表、表格、代码块、链接，几乎覆盖了 Agent 被要求产出的一切，这也是为什么一份 [Markdown 速查表](/zh/blog/markdown-cheat-sheet)能塞进一页纸，而 HTML 参考手册永远做不到。格式小、表面积小、在任何平台上意外都少。

当一个 AI 步骤的产出要被另一个 AI 步骤消费时，没有任何人类会看到这份文档，视觉层级一文不值。要紧的是 token 重量和可解析性，而 Markdown 在这两项上都贴近下限。[Markdown Guide 的入门页](https://www.markdownguide.org/getting-started/)指出，这个格式的设计目标就是让原始源码在渲染之前也读得通——这条特质机器消费者用不上，但随之而来的 token 效率它非常用得上。一份 HTML 交接文档则要为没有任何读者会看的包裹层、样式和语义付钱，而且每一代生成都付一次。

快速笔记和早期草稿补全了这一类。让 Agent 头脑风暴十个点子、列一份项目大纲，需要的是生成快、改起来不费事、在已经开着的任何编辑器里都能直接读——Markdown 三项全占，地球上随便哪个文本编辑器都行。一张看一遍就删的清单，不需要折叠区块。

这一类的共同规律：输出要被编辑、进版本管理、或交给机器消费时，Markdown 赢。这一点没有变过——HTML 那边的全部论点，也没有一条碰到它。

## 4. HTML 值回票价的地方：报告、评审、原型与可分享成果

Agent 输出的另一半干的是另一种活：有人得查看、对比或交互。2026 年的真实转变发生在这里，而 Markdown 的美德——朴素、极简、对编辑器友好——在这里不再是美德，开始变成天花板。

想想任何一份需要人扫读并据其行动的东西：季度评审、审计摘要、调研综述。Markdown 给读者的是标题、加粗和列表，说白了就是一次长滚动加一句祈祷。HTML 给同样内容的则是锚点链接、目录、视觉分组，以及眼睛在大脑开始阅读之前就能分好类的优先级信号——用 Markdown 呈现的季度评审是一次滚动，用 HTML 呈现的同一份评审是一个仪表盘。这个差别不是化妆，它直接决定这份文档是被认真读、被略读、还是被跳过。

代码评审是最锋利的例子。[Thariq Shihipar 的 AI 生成 HTML 示例集](https://thariqs.github.io/html-effectiveness/)里有带内联 diff 批注、按颜色标出严重程度的 PR 评审——那是 Markdown 字面上无法表达的信息架构，因为它没有「把这两样并排放、把左边那个涂成红色」的语法。以颜色抵达眼睛的严重程度，几秒内就完成分诊；用散文拼出来的严重程度，得一行行解析。对一份全部目的就是帮评审者决定先看哪里的文档来说，布局不是装饰——布局就是活本身。

还有一类输出根本不是文档。如果 Agent 能产出一个能跑的 HTML 原型——落地页、表单、仪表盘布局——那它是一个交付物：你可以在浏览器里打开它、摆到客户面前、在下一轮对话里继续迭代。Markdown 做不了这个活，出价多高都不行；它描述结构，但不表演任何东西。当「试一试」比「读一读」更重要的那一刻，格式问题就自己回答了自己。

可移植性是 HTML 最低调的优势，也是 Markdown 最少被讨论的弱点。一个内联 CSS 的 HTML 文件走得动——发邮件、在任何设备上打开，它自己渲染自己，因为浏览器就是渲染器；[现在已经有一整类工具专门把工作成果交付成这种自包含的单文件页面](/zh/blog/html-anything-review-2026)。Markdown 没有这种独立性：它需要一个引擎才能「像样」，而[GitHub 的 Markdown 渲染](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)不等于 Obsidian 的，Obsidian 的也不等于 Notion 的——脚注语法、任务列表、表格行为、数学公式支持全都随引擎而变，所以同一个 .md 文件可能在这个工具里干净、在那个工具里散架。这种引擎依赖是「交付用 HTML」最强的论据，也是一个能一致渲染两种格式的工作区——[Floatboat 的免费网页版 Markdown 工具](https://floatboat.ai/zh/tools/markdown)和桌面端都做得到——值得留在交接环节的原因：它把「这份文件会撞上哪个引擎？」的赌局，从每一次分享里拿掉了。

这一节的规律与第 3 节镜像：输出要被人阅读、对比、据其行动时，HTML 配得上那份额外的重量。

## 5. Token 成本与维护：方向比倍数更重要

拒绝说一句「看情况」就走人，也意味着拒绝编造精度。这场讨论里流传的倍数差异太大，没法诚实地复述，所以下面讲的是方向——它是稳定的——加上一套生成你自己数字的办法，而那才是真正能用来做决定的东西。

同样的内容，HTML 的输出 token 通常比 Markdown 贵。每一个包裹层、区块边界、样式属性、内联 CSS 规则都是一个 token，而它们没有一个是内容本身；它们是内容外面的脚手架。Markdown 的标记每个结构一两个字符——一个井号、一条短横线、一个反引号——同样的信息以低得多的开销搭车。这个方向在各家模型上都成立；幅度则取决于写 HTML 的习惯有多重样式。

篇幅会放大差距。三段话的摘要上，两种格式的 token 差距是噪声——舍入误差上的舍入误差。而在一份带表格、颜色编码和导航的二十节实施方案上，差距是真金白银，而且恰好随着「当初选 HTML 的那些视觉结构」的累积而变宽。量级还会复利：一条每天产出几十份成果物的流水线，感受得到单文档差距；单人创业者的某一次性交付物，永远感受不到。

诚实的检验是你自己的测试，五分钟就够：同一个提示词跑两种格式，在你实际用的模型里对比 token 数。输出侧按 token 计费——[Anthropic 的 API 定价文档](https://docs.anthropic.com/en/docs/about-claude/pricing)是他们那边计费方式的权威参考——所以更长的 HTML 输出按比例更贵，而你自己量出的数字胜过任何人发布的倍数。对大多数生成单份交付物的单人创业者，这个差距小到值得换那份可读性；对高产量流水线，它是一个值得先量再全面押注 HTML 的成本项。

成本不只是 token——维护会把它复利化。Markdown 文件对手改非常宽容：打开、修好、保存，完事，什么编辑器都行。自包含的 HTML 文件则惩罚随手编辑——删错一个闭合标签、挪错一条样式规则，布局就肉眼可见地坏了，这时候你是在调试一份文档，而不是在修订它。当一份 HTML 成果物真的需要动大手术，务实的路线往往是先把 [HTML 转回 Markdown](/zh/blog/convert-html-to-markdown)，在改起来便宜的地方把内容改好，等尘埃落定再重新生成 HTML。选择的依据是：你会编辑这份输出（Markdown），还是原样消费它（HTML）——契合度比功能重要。

## 6. 四问决策框架

速查表覆盖标准情况；有意思的情况需要问题。如果你经营着一人的公司——内容、策略、交付，全是你——格式选择一天要出现好几次，所以它必须快，还必须扛得住边界情况。按顺序问下面四个；顺序有意义，因为每个问题淘汰一种不同的错误答案。

1. **谁读这份输出？**只有你自己，或链条里的另一个 Agent，就用 Markdown——没有人类的眼睛，视觉层级一文不值。如果有客户、协作者或受众会读，HTML 就进入了讨论，因为他们的阅读体验本身就是交付物的一部分，不是外围的加分项。

2. **生成之后还会被编辑吗？**Markdown 的修订在任何文本编辑器里都能做，diff 里也干净——这就是为什么所有「活的」东西——文档、规格、笔记——都该归它。一份定了稿、不会再变的交付物，用 HTML 更能守住排版——这个格式生来就是为了在任何地方被任何东西打开。

3. **它需要视觉结构吗？**平铺列表、大纲、成段的文字，是 Markdown 的主场。内容一旦需要标签页、颜色编码、并排对比或导航，它就越过了 Markdown 的表达力边界——再细心的排版功夫也替代不了真正的布局。

4. **它会被复用或模板化吗？**反复产出、又要求视觉一致的那类输出——周报、审计报告、状态摘要——值得模板化，聊天侧的 Artifacts 类功能或本地优先的 Agent 化 HTML 编辑器可以承载这个模板，让每一次生成都长得像上一次。一次性请求不需要那套基础设施，为它搭建是交税，不是投资。

这个顺序是刻意的：观众决定大类，后面三问在大类内部裁决边界情况。拿具体的东西跑一遍——客户入职清单、每周营收摘要、迁移方案——你会注意到，很少有问题需要问到第四问答案才浮出来。这种速度正是意义所在：一套你在写提示词中途就能执行完的框架，胜过一套完美但需要查手册的框架。

四问产出的默认做法是混合式的，值得当成一条规则来记：Markdown 里起草和迭代，交付给人的时候转换或精修成 HTML。思考阶段——内容每九十秒变一次的时候——你享受 Markdown 的可编辑性；交付阶段——内容稳定、读者的注意力成了稀缺资源的时候——你享受 HTML 的可读性。起草那一侧永远便宜——[Markdown 是什么、又为什么普及开来](/zh/blog/what-is-markdown)是一门小到一下午就能吃透的语言——只有交付这一步付 HTML 的溢价，而且只在真的有人在等的时候付。

这条混合规则也顺带说明了工具该长什么样。一个两种格式并排存在的工作区——比如 Floatboat 的桌面端和免费网页工具，在同一个文件树里渲染 Markdown、处理 HTML 成果物，草稿和交付物之间没有导出仪式——恰好对应这个选择在现实中的运行方式：按活选，不按人选。周一的内部笔记和周四的客户报告，不再是一个工具决策，而是变回它本来的样子：一个格式决策。任何强迫你对某一种格式宣誓效忠的工具，都在为你本不必做的决定收费。

## 7. 结论

剥掉争论的外壳，这个操作层的问题小到一只手就握得住：要被编辑、看 diff、被解析的输出，是 Markdown 的活；要被人读、被对比、被据以行动的输出，是 HTML 的活。把你最近让 Agent 产出的十样东西翻出来，按「接下来发生了什么」分个类——分类只要一分钟，它告诉你的是你个人的配比，这是任何一篇博客都给不了的。然后对下一份输出跑一遍四问；实践中答案通常在第二问就到，而那个罕见地撑到第四问的情况，恰恰值得你放慢脚步。格式之争会一直循环，但这条决策法则不会过时：契合度比功能重要，而你眼前的活，永远知道它需要哪个格式。
