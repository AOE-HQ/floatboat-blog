Kimi K3 是 Moonshot AI 面向长时编程、知识工作、视觉理解与推理的模型。Moonshot 公布了 100 万 token 上下文窗口和 `kimi-k3` 模型 ID。这些能力适合大型代码仓和文档密集型任务，却不代表 Kimi K3 已经成为 Floatboat 可直接选择的模型。

**信息核对截至 2026 年 10 月 13 日。**Floatboat 已确认的运行时矩阵只为 `kimi-k3` 登记了底层容量与预算支持，尚未在客户端默认选择器露出。用户不应预期界面中已经出现 Kimi K3 按钮，也不应把本文理解为上线公告。

## Kimi K3 已确认的规格

Moonshot 的[Kimi K3 官方公告](https://forum.moonshot.ai/t/kimi-k3-is-here-our-most-capable-model/480)列出：

| 项目 | Kimi K3 |
|---|---|
| 模型 ID | `kimi-k3` |
| 参数量 | 2.8 万亿 |
| 上下文窗口 | 100 万 token |
| 输入能力 | 文本与原生视觉 |
| 主要任务 | 长时编程、知识工作、推理 |
| 推理力度 | `low`、`high`、`max` |
| 公告时 API 标价 | 缓存输入 $0.30、非缓存输入 $3、输出 $15 / 百万 token |

这里的价格属于 Moonshot API，不是 Floatboat 价格。Moonshot 还提醒，多轮对话应回传完整 assistant message，也不要在进行中的会话里从其他模型切换到 K3。这些是 API 集成要求，不能用来推断 Floatboat 将如何开放模型。

## Floatboat 的“底层容量已登记”是什么意思

Floatboat 运行时为 `kimi-k3` 设置了 100 万 token 预算，经济画像也兼容 `kimi-k2`、`kimi-latest` 等别名。这使平台能在评测或未来路由时估算上下文与成本。

但它还不能证明用户侧上线所需的三件事：

- 选择器中已有可见入口；
- 已公布套餐或资格门槛；
- 已通过 Floatboat 托管网关建立生产路由。

基础设施准备往往早于产品发布，营销文案不能把二者合并。

## Kimi K3 可能适合哪些任务

当任务确实需要巨大工作集时，100 万上下文才有意义，例如同时审阅大量关联文档、连同设计记录一起理解代码仓，或在长篇研究材料中比对证据。原生视觉也允许截图、图表和界面图片参与同一条推理链。

长上下文不能替代检索与筛选。无关材料会让结果更难审计，也可能增加成本。可靠评测应比较“全部塞入上下文”与“只检索相关片段”两种方案，再衡量事实覆盖、引用、延迟和人工复核时间。

推理力度同样应按任务选择。只有质量收益超过额外延迟和输出成本时，才值得使用 `max`；常规提取、分类和格式转换应从低档开始。

## 模型存在与产品接入不是一回事

模型本身可以很强，但产品接入仍未完成。一次真正的 Floatboat 上线必须说明准确 Model ID 与显示名称、入口位置、访问门槛、路由与降级方式，以及托管服务是否需要单独 API Key。

这些信息公布前，“无需 API Key”“自动路由”“所有用户可用”都没有得到验证，不能从内部容量记录反推。

## 上线前可以准备怎样的评测

对 Kimi K3 感兴趣的团队可以先准备五类用例：跨文件修改并验证的代码任务；必须引用多份来源的文档任务；截图结合书面要求的视觉任务；同时放入相关与无关材料的长上下文压力测试；以及不同推理档位和缓存假设下的成本比较。

评分对象应是最终成果、证据质量、工具可靠性、延迟和人工修正时间，而不是把“100 万上限”本身当作质量指标。

## 结论

Kimi K3 是一款规格突出的 Moonshot 模型：2.8 万亿参数、原生视觉、100 万 token 窗口，以及面向长时任务的推理控制。Floatboat 已为 `kimi-k3` 准备底层容量，但截至 2026 年 10 月 13 日，它不在客户端默认选择器中。

准确口径是“技术准备”，而不是“正式发布”。Kimi K3 值得进入 Floatboat 的评测路线图，却不应被宣传成所有 Floatboat 用户已经可以选择的模型。
