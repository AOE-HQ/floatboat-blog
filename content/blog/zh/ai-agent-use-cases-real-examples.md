最值得落地的 AI Agent 场景，不是步骤最多、看起来最自主的那个，而是一项重复出现的工作：输入拿得到，工具权限可控，结果可以验证，并且清楚知道哪一步必须由人负责。

本文把公开记录的案例与示例工作流分开。没有 Nova 的个人实测，也不使用虚构人物和无来源的「节省几小时」。目标是帮你选出一项能够面对真实文件、权限、异常和审阅的首个用例。

## 自动化之前，先做五项判断

| 问题 | 适合的信号 | 危险信号 |
|---|---|---|
| 输入 | 结构化工单、文件夹、Brief、事件或固定 URL | 目标只存在某个人脑中 |
| 工具 | 身份明确、范围有限的读写动作 | 不清楚 Scope 的全账号访问 |
| 输出 | 工单结案、测试通过的改动、带来源简报、可编辑文件 | 没有验收标准的「有用洞察」 |
| 人工门禁 | 对外或不可逆动作发生前审批 | 发布后人才第一次看到结果 |
| 反馈 | 测试、状态检查、Rubric 或审阅决定 | Agent 自己给自己的工作打分 |

任务不必完全确定，但必须有足够的环境事实判断它是否在向目标推进。Anthropic 把客户支持和编码列为较适合 Agent 的领域，原因正是它们同时具备工具、反馈循环和可衡量的结案或测试结果（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。

## 已公开案例一：调用工具处理客户支持

Anthropic 描述过一种具有生产形态的客服 Agent：对话提供诉求，工具读取客户、订单与知识库，后续动作更新工单或退款。输出是明确的处理状态，而不是一篇泛泛建议。

- **输入：**客户消息、账号身份、政策和订单历史。
- **工具：**知识检索、账号查询、工单更新、限额退款。
- **输出：**回复与更新后的 Case 状态。
- **人工门禁：**例外、大额退款、政策覆盖、敏感账号。
**失败模式：**匹配错客户、使用旧政策、工单文本中的 Prompt Injection、重复写入、看似完整但漏处理。

真正的设计重点不是「让 AI 回工单」，而是把读取与高后果写入分开。Agent 可以自动收集证据和起草方案，退款和账号变更仍由策略层或人控制。

## 已公开案例二：围绕测试循环修改代码

仓库、Issue、工具与测试套件可以形成紧密反馈，因此编码是典型 Agent 场景。Agent 能改文件、运行测试、读取失败并继续迭代；但 Anthropic 同时强调，测试无法覆盖的产品要求仍需要人工审查。

- **输入：**Issue、代码仓库、项目规则、当前分支。
- **工具：**搜索、文件编辑、Shell、测试、版本控制。
- **输出：**Diff、测试证据与待审改动。
- **人工门禁：**依赖变更、密钥、Push、PR、Merge 与部署。
**失败模式：**只针对可见测试优化、修改无关文件、引入安全问题、重复危险命令、测试通过但违背产品意图。

这里也能看出 [Agent Harness](/zh/blog/what-is-an-agent-harness) 的作用：模型负责写代码，Harness 提供 Sandbox、命令策略、检查点、Trace 和审批边界。

## 已公开案例三：定时运营检查

Raycast 2026 年 9 月的 Windows 更新日志列出了团队内部使用 Automations 的例子：每天早上整理邮箱、每小时检查开放中的 PR、每天晚上从会议笔记更新 Memory（[Raycast Windows 更新日志](https://www.raycast.com/changelog/windows)）。这些是厂商自行披露的使用方式，不是独立效率测量，但任务结构值得参考。

- **输入：**时间表与范围有限的邮箱、PR 列表或笔记位置。
- **工具：**邮件或代码仓 Connector、搜索、状态读取、项目记忆写入。
- **输出：**分类队列、异常通知或更新记录。
- **人工门禁：**发送回复、合并代码、删除邮件、把推断写入权威记忆。
**失败模式：**重复运行、设备休眠、凭据过期、告警过多、状态过期、静默漏项。

系统必须区分「没有变化」和「检查失败」，否则安静的一天与坏掉的 Automation 看起来完全相同。

## 示例工作流四：从调研到客户简报

以下是示例流程，不是客户成果。它适合 Agent Workspace，是因为来源、规则、草稿、审阅和最终文件需要保持关联。

- **输入：**获批 Brief、资料文件夹、调研问题、引用规则。
- **工具：**网页搜索、文档读取、笔记和文件写入。
- **输出：**带引用的研究简报，明确标出未解决问题。
- **人工门禁：**来源取舍、解释、关键主张和客户交付。
**失败模式：**来源不可访问、引用二手转述、事实过期、引用漂移、综合过浅。

较安全的顺序是：先定义问题，收集候选来源，确认取证范围，逐项提取带出处的主张，再起草、核对引用和人工审阅。Floatboat 的公开 Agent Workspace 页面也展示了类似的 Research-to-delivery 流程：授权材料、Agent Runs、审阅与可编辑交付物留在同一项目里（[Floatboat Agent Workspace](https://floatboat.ai/agent-workspace)）。

## 示例工作流五：长内容的渠道改写

有现成原稿，不代表「生成五条帖子」已经是一条可靠流程。

- **输入：**获批原稿、受众定义、渠道限制和不得改变的主张。
- **工具：**文档读取、Style Guide、草稿生成与链接检查。
- **输出：**按渠道写成、且能映射回原文依据的草稿。
- **人工门禁：**定位、敏感主张、品牌表达与发布。
**失败模式：**所有渠道套同一种框架、编造案例、删掉限定条件、发布失效链接。

验证器应检查事实忠实度，而不只是语言是否流畅。审阅时要能回答：每项主张来自原文哪里，为当前受众主动省略了什么。

## 示例工作流六：竞品页面变化监控

监控适合让 Agent 发现变化，让人解释变化。

- **输入：**明确 URL、抓取周期、基线快照与变化分类。
- **工具：**浏览器、页面快照、Diff 与通知。
- **输出：**附日期和前后证据的变更记录。
- **人工门禁：**战略解读与后续反应。
**失败模式：**动态页面噪声、地区版本、访问受阻、页面遗漏、虚假的「无变化」、把文案改动直接解读成战略。

原始快照必须保留。没有证据的摘要无法审计，Agent 也不应从表层变化推断竞品意图。

## 用选择矩阵确定第一个 Pilot

| 候选场景 | 可验证性 | 风险 | 搭建成本 | 首次试点 |
|---|---:|---:|---:|---|
| 工单分类与路由 | 高 | 只读时低 | 中 | 适合 |
| 起草带引用的研究简报 | 中高 | 中 | 中 | 审阅后适合 |
| 修改代码并运行测试 | 高 | 中 | 中 | Sandbox 中适合 |
| 监控指定网页 | 变化检测高 | 低 | 低至中 | 适合 |
| 起草对外消息 | 中 | Send 环节高 | 低 | 先只生成草稿 |
| 修改生产记录 | 中 | 高 | 高 | 不适合首个 Pilot |
| 作出招聘、医疗、法律或金融决定 | 缺少专家流程时低 | 极高 | 高 | 不委托最终决定 |

首个试点应优先选择重复、边界清楚、可撤销、容易检查的任务。频率不是唯一条件：每周一次但验证清楚的任务，可能优于每天发生但成功标准主观的工作。

## 围绕失败设计试点

1. **先写验收条件：**明确定义正确 Artifact 或状态变化。
2. **选择十个代表性样本：**包含缺数据、指令冲突，以及一个应该拒绝的案例。
3. **从只读或只生成草稿开始：**不要一边学习流程，一边开放宽泛写权限。
4. **记录完整运行：**输入、工具调用、审批、输出、错误、时间与成本都要留下。
5. **主动制造中断：**让凭据失效、移除来源，或在写入前停止进程。
6. **同时检查误报与漏报：**「大部分不错」可能掩盖最重要的一类错误。
7. **每次只扩大一项权限：**上一层边界可靠后再开放写入。

Pilot 结束后的选择不只是上线或放弃。Agent 可以继续负责研究、草拟或发现异常，而固定 Workflow 或人拥有最终修改权。

## 用结果指标代替无依据的「省时」

不要预设节省几小时。先测同一任务的基线，再记录无需大改即可采用的产出、事实或政策错误、人工审阅时间、中断恢复率、重复或越权动作、总成本、正确升级给人的案例，以及从输入到验收结果的时间。

必须计算搭建与复核。起草更快，但验证更慢，整个流程仍可能亏损。

## 哪些位置必须由 Agent 停下来

Agent 可以为高后果决策准备证据，但不能因此拥有最终决定。招聘、医疗、法律、金融、访问控制与生产变更，需要领域规则和明确责任人。「Human in the loop」必须指出具体由谁决定什么，并发生在不可逆动作之前，不能只是事后免责声明。

Connector 也应同样审查。Agent 能修改 Gmail、GitHub、CRM 或数据库之前，应核对身份、Scope、资源权限、审批、日志与撤销路径。[Agent Connector 指南](/zh/blog/ai-agent-connectors-explained)详细解释了这套边界。

## 从一项能够证明完成的工作开始

可落地的 AI Agent 场景通常都有同一组条件：输入有边界、工具清楚、状态可观察、结果能验证、人工责任明确。客服结案、测试驱动的代码修改、定时检查、带引用调研、内容改写和页面变化监控都可以成立，前提是流程没有隐藏失败。

不要先问 Agent 理论上能做什么。列出重复工作，按可验证性和风险排序，再试点其中最安全且有价值的一项。第一个真正有用的 Agent，通常不是自主程度最高的那个，而是每次运行都能检查、修正，并逐步建立信任的那个。
