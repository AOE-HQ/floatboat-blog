Agentic AI 系统的自研还是购买，并不是“定制但强大”和“现成但受限”的二选一。真正要决定的是：哪些控制面必须由组织掌握，哪些可以交给供应商更有效地运营。

现实中有三条路线：

- **自研：**自己负责应用、编排、集成、状态、控制与运行。
- **购买：**配置托管产品，并接受其执行、身份、数据和发布模型。
- **混合：**掌握任务契约、政策、评估和差异化逻辑，同时购买模型、运行时、可观测性、连接器或工作区界面。

对不少团队而言，混合架构可以作为待验证的起点，但不是默认正确答案。最终选择应来自同一条真实工作流的证据。

## 先判断是否真的需要 Agentic 系统

Anthropic 的[有效 Agent 工程指南](https://www.anthropic.com/engineering/building-effective-agents)建议从能够完成任务的最简单方案开始。边界清楚的一次转换只需要单次模型调用；路径已知的多步骤任务适合确定性工作流；只有执行路线无法预先规定、模型需要根据环境反馈选择工具时，Agent 才有必要。

当 Agent 需要持久状态、多项集成、多人共用、权限、评估、监控、发布控制和恢复时，它已经是一套系统。门槛不是 Agent 的数量；一个会改变生产环境的 Agent 也需要系统工程。

比较供应商或框架前，先写任务契约：输入和触发、可接受结果与证据、允许读取和执行的范围、人工审批点、停止和预算上限、恢复与升级方式、数据分类和保留政策，以及最终责任人。

这些字段如果不清楚，采购评分表比较的只是演示效果。

## 三条路线分别掌握什么

| 层面 | 自研 | 购买 | 混合 |
|---|---|---|---|
| 任务与产品行为 | 团队掌握 | 在产品范围内配置 | 团队掌握差异化逻辑 |
| 模型与编排 | 团队选择并运营 | 厂商运营 | 按组件拆分 |
| 身份与权限 | 团队集成并执行 | 依赖租户控制与产品能力 | 企业身份加托管运行时 |
| 连接器 | 自建或单独采购 | 使用厂商目录 | 通用的购买，关键的自建 |
| 状态与成果 | 团队定义存储 | 由产品定义存储和导出 | 可迁移事实源加托管执行 |
| 评估 | 团队必须建设 | 厂商可提供工具，成功标准仍归团队 | 团队掌握案例，基础设施可托管 |
| 可靠性与恢复 | 团队端到端负责 | 依赖合同与产品控制 | 明确边界与共同运行手册 |
| 发布节奏 | 团队控制 | 厂商控制 | 双方通过版本化接口连接 |

“自研”不等于没有供应商，通常仍依赖托管模型、云、数据库、身份服务和框架。“购买”也不等于没有工程工作，集成、权限、验收、事故响应和变更管理依然属于你。

## 按任务形态和战略差异选择

任务普遍、产品已支持所需系统、配置能够表达政策，而且替换实现不会丢掉竞争优势时，购买值得优先验证。例如内部检索、会议准备、标准工单分类和套件内草拟，前提是通过数据与权限审查。

如果 Agent 承载专有决策逻辑，需要特殊工具或受限环境，或者对延迟、可用性、审计和恢复的要求超出托管产品保证，自研更可能合适。

当业务逻辑具有差异化、基础设施却很通用时，可以考虑混合。团队掌握资格政策、工具结构、评估集和事实源，同时采用托管模型、持久运行时或连接器服务。

不要把“流程复杂”误当成“自研有战略价值”，也不要把供应商勾选的一项功能误认为它能覆盖你的真实例外。

## 治理责任无法外包

NIST 的 [AI 风险管理框架](https://www.nist.gov/itl/ai-risk-management-framework)用 Govern、Map、Measure、Manage 组织风险工作。购买软件并不会让这些职责消失。供应商可以提供控制和证据，但用途、风险容忍度、人的角色以及是否继续部署，仍由采用方决定。

无论哪条路线，都要确定：系统和风险责任人、预期和禁止用途、受影响用户与数据类别、模型工具连接器清单、最小权限身份、按操作影响划分的审批、评估和监控责任人、事故回滚与离职交接流程，以及厂商变更和弃用处理方式。

不要为了安装方便就开放整个工作区、邮箱、CRM、浏览器或数据库。区分读取、草稿、可逆写入和高影响写入。购买的平台必须能够收窄身份并检查行动；自研系统则必须在模型循环外执行授权。

## 集成不能只数连接器图标

连接器目录经常掩盖真正困难的部分。每项必需集成都要核对：

| 问题 | 为什么重要 |
|---|---|
| 认证方式 | 用户委托、服务身份和共享凭证的风险不同 |
| 权限粒度 | 一项窄任务可能被迫开放整个账号 |
| 读写范围 | “支持 CRM”可能只支持搜索，不支持目标动作 |
| 事件行为 | 轮询、Webhook、顺序和重复投递会影响正确性 |
| 错误契约 | 稳定错误类型和外部 ID 才能安全重试 |
| 限速与载荷 | 演示数据量未必代表生产环境 |
| 版本管理 | API 或结构变化可能让流程静默损坏 |
| 审计证据 | 必须知道哪个身份修改了哪条记录 |

为真实操作写一组最薄的集成测试，覆盖凭证过期、权限缺失、事件重复、结构变化、部分响应，以及外部写入成功后本地超时。

## 所有方案共用一套验收评估

如果自研原型和托管演示处理的任务不同，比较就没有意义。建立一套包含正常、边界、对抗和恢复案例的数据集，让每个方案在安全环境中运行。

Anthropic 的 [Agent 评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分任务、多次试验、评分器和完整轨迹；OpenAI 的 [Agent 评估文档](https://developers.openai.com/api/docs/guides/agent-evals)也建议用轨迹评分检查工具选择、交接、指令违规和端到端行为。

衡量可接受结果率、人工修正时间、来源质量、工具与参数准确性、权限或政策违规、干预和升级率、重复或遗漏的副作用、每个可接受结果的延迟和成本、恢复时间，以及第二位运维人员解释运行过程所需时间。

对有随机性的案例应重复运行。一次成功演示只能证明某条路径存在，不能证明服务可靠。

## 总拥有成本必须按真实负载建模

不要相信“购买几天上线”或“维护费固定占开发费多少”一类通用数字。TCO 取决于负载、控制要求、团队能力和合同条款。

**自研 TCO**包括需求发现、工程、评估、基础设施、模型调用、集成、安全审查、值班、维护、迁移和机会成本。

**购买 TCO**包括许可、用量或积分、高级模型、连接器、实施、治理、人工复核、超额费用、支持和退出成本。

**混合 TCO**还要计算边界工作：接口版本、重复日志、厂商协调和对账。

按预期、低谷与峰值容量计算每个可接受业务结果的成本，把失败和复核率纳入。价格使用带日期的厂商报价核实，不要把容易变化的数字写死在架构决策中。

成本也不只是支出。探索阶段看获得学习的速度；规模化阶段看单位经济是否可预测；稀缺工程时间还有其他用途。

## 拥有代码不等于可迁移

自研系统可能被云服务、模型 API、框架、数据库结构或少数工程师的隐性知识锁定；托管产品则可能把价值锁在专有流程、对话、权限、连接器映射和运行历史里。

| 资产 | 可迁移性测试 |
|---|---|
| 任务契约和政策 | 另一个运行时能否执行？ |
| 提示词和工具结构 | 能否以可用形式导出？ |
| 评估 | 同一批案例能否在别处运行？ |
| 项目数据和成果 | 格式、关系和权限能否保留？ |
| 状态和运行历史 | 未完成工作与证据能否重建？ |
| 身份与凭证 | 能否彻底撤销并重新分配？ |
| 业务逻辑 | 是否与厂商专属节点分离？ |

有导出按钮不等于有退出方案。用第二套技术栈复建一条代表性任务，并实际恢复一份小型导出，才能验证可迁移性。

## 一种边界清楚的混合架构

混合架构只有在责任边界明确时才成立。一种常见方式是：

1. 企业掌握任务契约、政策、评估集和事实源 ID；
2. 托管模型或 Agent 运行时在窄工具目录中规划并执行；
3. 企业控制的网关负责认证、授权、校验和工具日志；
4. 高影响写入暂停等待审批；
5. 持久状态记录检查点与外部副作用 ID；
6. 接口版本化，使运行时可以替换。

它不会天然更便宜或简单。它的价值在于保留差异化逻辑和治理的可迁移性，同时外包通用运维。

## 运行一次自研与购买选型试点

使用同一任务和验收集开展有时间边界的试点：

1. **建立基线：**测量现有人工或工作流的可接受结果、复核时间、故障、容量和服务要求。
2. **选择候选：**包含最小可行自研与一到两个托管选项；只有边界清楚时才加入混合方案。
3. **通过治理与集成门槛：**核验身份、权限、保留、审计、事故处理、数据条款和退出规定，并测试真实写入。
4. **运行影子与草稿模式：**接收真实输入但不做高影响写入，再逐步开放经审核的草稿或可逆操作。
5. **主动制造故障和变化：**撤销权限、重复事件、改变数据结构、中断写入、更换模型并导出成果。
6. **比较证据：**评估质量、风险、集成适配、运维负担、TCO 情景和退出准备度，并写下复审日期。

## 决策矩阵

| 试点证据 | 倾向 |
|---|---|
| 通用任务、产品适配强、控制可接受 | 购买 |
| 专有行为、特殊环境、严格运行保证 | 自研 |
| 差异化逻辑加通用基础设施 | 混合 |
| 需求仍频繁变化、评估证据很少 | 窄范围购买或原型，推迟不可逆架构 |
| 没有方案满足权限或恢复要求 | 暂不部署 |

若要深入自研路径的工程生命周期，可看[如何构建 AI Agent](/zh/blog/how-to-build-an-ai-agent)；若需要区分托管项目上下文与流程自动化，可比较[工作流构建器与 AI 工作区](/zh/blog/workflow-builder-vs-ai-workspace)；若评估的是开发服务商而不是产品，可参考[定制 AI Agent 开发指南](/zh/blog/custom-ai-agent-development)。

## 最终决策是长期所有权

当行为和运行控制具有战略价值、团队也确实能运营时，选择自研；当托管产品覆盖任务，治理和退出条件也通过审查时，选择购买；当清晰边界能让团队保留政策、证据和差异化，同时避免重建通用基础设施时，选择混合。

无论走哪条路线，都应自己掌握任务契约、评估集、权限模型、运行证据和退出计划。它们才是一套 Agentic AI 系统最耐久的资产。
