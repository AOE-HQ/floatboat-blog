## TL;DR

- **Markdown 笔记工作流，就是把笔记保存为纯文本 `.md` 文件，靠命名规范、标题分层和笔记间链接来组织——不管当下用哪个应用渲染，笔记本身几十年后依然可读。** 工作流核心是三个习惯（一致的文件名、一个文件一件事、用链接代替文件夹），渲染器随便挑。
- 它消灭的失败模式是锁定：笔记应用会停服、被收购、改价格、导出成灾难。一个 `.md` 文件夹没有这些失败模式——[Markdown 是什么](/zh/blog/what-is-markdown)解释了为什么格式本身就是安全网。
- 核心工作流一个下午搭完：一个笔记文件夹、一套命名规范、文件内的标题结构，以及用链接代替深层文件夹的关联方式。
- 同一个笔记库可以直接变成 AI 工作区：能读取笔记文件夹的 agent，可以基于你已经信任的材料做摘要、交叉检索和起草。
- 从任何编辑器起步都行——文件优先，应用可换。

## 1. 纯文本笔记的 case

每一款笔记应用都做过同一个承诺：你的知识，永久有序。兑现记录参差不齐。服务被收购后关停、定价层级说变就变、私有数据库导出成灾难，而「导出」通常给你一份丢失了多年积累的链接和格式的 HTML 或 JSON。到 2026 年，笔记应用坟场已经大到让锁定风险成为选型的第一标准，而不是事后才想的细节。

Markdown 笔记押的是相反的方向。笔记就是一个文本文件。所有操作系统、所有编辑器、所有编程语言、所有 AI 模型都能读它。今天用的应用明天消失，笔记纹丝不动——换个工具打开，继续写。这个格式比大多数笔记应用都老，也会比它们全都活得久；Markdown 这一路是怎么走过来的，本质上就是「一个格式熬过一波又一波工具」的历史。

还有第二个更安静的优势：文件化的笔记可以 grep。当知识库是一个 `.md` 文件夹，全文搜索即时完成，备份就是复制文件夹，版本历史可以简单到只是一个 git 仓库。这些都不需要笔记应用批准。

## 2. 一套能熬过应用更替的工作流

工具不重要，习惯才重要。以下四个习惯决定了笔记库几年后还能不能用。

**一个文件一件事。** 一个叫 `2026-09-05 客户入职清单.md` 的笔记，胜过一个四百行、名叫「杂记」的文件。一个文件一件事，后面的链接、重命名、AI 摘要才成立——一个只说一件事的笔记，才能被单独链接、单独移动、单独喂给 agent，而不会拖出一堆不相关的内容。

**时间型笔记加日期前缀。** `2026-09-05 会议记录.md` 在任何文件浏览器里都按时间排序，零功能依赖。主题笔记（`markdown-工作流.md`）按字母排序，活在日期流之外。两种命名模式几乎覆盖所有场景。

**链接优于文件夹。** 深层文件夹逼你做选择——这条笔记归「客户」还是归「项目」？链接不需要做这个选择。一条笔记平铺在库里，可以被三个地方链接。在 Obsidian 一类的工具里，`[[双链]]` 一次按键完成；在纯 Markdown 里，指向文件的普通链接在所有地方都有效。如果你好奇 [Obsidian vault 到底是什么](/zh/blog/what-is-obsidian-vault)，一句话版本：一个 Markdown 文件夹，笔记之间的链接才是真正的结构，应用只是把它渲染出来。

**文件内部用标题，别只靠文件名。** `## 背景`、`## 决定`、`## 下一步`——一致的内部标题让一年后的笔记依然可扫读，也正是工具（和 AI）可靠地切分、引用你笔记的依据。

标签系统可以作为补充，但标签是最不可移植的一层：每个应用实现都不一样，有些还存在私有数据库里。链接和标题活在文件内部——这就是工作流依赖它们的原因。

## 3. 四种命名系统，以及它们五年后的样子

命名是笔记库采纳的第一条约定，也是最后才被重新审视的一条——正因如此，它值得一个经过思考的选择，而不是「第一个文件碰巧怎么建的就怎么来」。主流的认真笔记库里流行四种系统：日期前缀、主题名、Johnny Decimal 分类码、Zettelkasten 编号。每一种都是对「这个库五年后会变成什么样」的一次押注，而这些押注的老化速度截然不同。决定可以按笔记类别分步调整——但四种混用、从不检视，才是五年老库变得不可用的最常见原因。

| 系统 | 文件长这样 | 适合什么 | 五年后 |
| --- | --- | --- | --- |
| 日期前缀 | `2026-09-05 客户电话.md` | 时间流：会议、日志、发票、记录 | 一条可翻阅的时间线；旧月份自然沉淀，任何日期几秒内可查 |
| 主题名 | `定价策略.md` | 常青参考：概念、清单、操作指南 | 一个按字母排序的个人 wiki；含义靠标题和链接承载，与位置无关 |
| Johnny Decimal | `12.04 供应商合同.md` | 结构稳定、每类不过百件的领域——档案、票据、税务 | 可预测但僵硬；要么一直整齐，要么在某个类目撑爆格子后被悄悄放弃 |
| Zettelkasten ID | `202609052130.md` 或 `f7k3qp.md` | 关系活在链接里而非文件名里的原子笔记 | 文件名沦为不透明句柄；标题和链接承担全部含义——对能解析链接的应用是优雅，对普通文件浏览器是灾难 |

日期前缀和主题名覆盖了大多数个人笔记库，而且分工干净：日期前缀管时间的流——价值与「何时发生」绑在一起的一切；主题名管知识——无论何时写下都成立的东西。五年后回看，日期流读起来像一本真的能翻的日志，字母序的主题架读起来像你为自己写的文档。这套搭配成立的原因在于：谁都不抢谁的活。

Johnny Decimal 和 Zettelkasten 编号是专家工具，都惩罚随手使用。Johnny Decimal 在领域结构真正固定的地方发光——税务不会重新谈判自己的类目——在持续演化的工作上卡壳，因为给一个成熟库重新编号是没人想花的那个周末。Zettelkasten 编号走向另一个极端：把文件名当作不透明句柄，含义完全活在标题和链接里——在能解析链接的应用里优雅，在普通文件浏览器里几乎没法读。五年之后，这两种系统呈现的往往是选择者的自律程度，而不是系统本身的高下。

上面这样的表格，只有在所有渲染器里都成立才值得写；如果表格语法还不熟，[Markdown 表格怎么做](/zh/blog/markdown-table-how-to)覆盖了三行结构、对齐冒号和竖线转义这些让表格跨渲染器不翻车的细节。无论选了哪套系统，把约定写进库根目录的 `README.md`。未来的你继承的是规则，不是感觉。

## 4. 一套不会烂掉的标签分类法

第 2 节说过标签是最不可移植的一层，但可移植性只是标签问题的一半——另一半是漂移（tag drift）。挺过迁移的标签系统照样可以在原地烂掉：同义词越积越多，范围越来越糊，一个二十个标签起步的词表长成两百个谁也记不住的标签。解法不是更好的软件，而是一小套治理规则——说起来便宜、执行起来便宜，并且按日程执行，而不是靠一年一度的愧疚爆发。

第一条规则：扁平优先于层级。`客户/acme/法务` 这样的嵌套标签在悄悄重建文件夹问题，工具还更差：各家应用分隔符不一致，有的渲染层级有的拍平，捕获时还要多记一层路径。扁平标签把含义收在标签词本身；当词表总想长出层级，那通常是个信号——这个概念值得拥有自己的一条笔记，一个被其他笔记链接的小枢纽页，就能干完标签树假装能干的活。含义属于文件和链接；标签只做最上面那层薄薄的贴纸。

第二条规则：词表设硬上限。每条笔记两三个标签足够检索用，一个活跃的库也很少需要超过几十个在役标签。一个可执行的门槛：值得保留的标签，至少被五条笔记使用；只被两条笔记用过的标签，其实是一条笔记标题的伪装。到顶之后，新建一个标签就得退掉一个旧的——这让词表始终保持一份咖啡订单的体量，而不是一本电话簿。

第三条规则：每月一次审计，在纯文本库里这只需要几分钟而不是一个下午。它每月固定在同一个时段运行，不跟正事抢时间，内容是几个机械动作：

- 同义词向自己实际会打的那种合并——用 `meeting`，而不是 `meeting` 和 `meetings` 并存。
- 用在不到三条笔记上的标签，并入最近的大标签，或者直接删掉。
- 重命名就是全文件夹一次查找替换，而不是回到某个应用里一条条重新打标。
- 归档笔记身上挂的标签顺手清掉；标签描述的是工作集，不是博物馆。

这些操作每一个都是文本操作——Markdown 里的标签以普通字符活在正文或 frontmatter 里，可以写成脚本、可以用 git 回滚、可以带去任何下一个工具。同样的审计在应用锁定的数据库里是一条笔记一次点击的苦役，这正是大多数标签系统从未被审计过的原因。便宜的治理才是全部诀窍，而便宜来自格式本身。

## 5. 附件、截图，以及大文件该去哪

「笔记文件夹里只有文本文件」的幻想大约能维持两周——然后第一张截图就到了。附件不可避免，所以真正的问题只有一个：它们的命名和摆放，是约定还是事故。可行的答案要在文件夹被 `Screenshot (23).png` 塞满之前决定，而不是之后：笔记旁边放一个 assets 文件夹，文件名说清「是什么、什么时候」，再划一条把大文件留在外面的硬线。

assets 文件夹约定无趣但正确。笔记旁边放一个 `assets/` 子文件夹，每条图片引用都指向 `assets/2026-09-05-仪表盘报错.png` 这样的相对路径，整个库就能作为单体移动——把文件夹拷到新机器或新应用，所有图片链接照样解析，因为没有任何东西指向文件夹之外。绝对路径和应用托管的附件仓库是两种悄悄破坏这一点的安排，而且都是常见默认值——值得在搭建时就改掉，而不是搬迁后再修。

截图值得享受和笔记同样的命名纪律：一个日期，加这张图实际展示的东西——`2026-09-05 仪表盘报错.png`，而不是 `Screenshot (23).png`。日期前缀对图片做的事和对笔记一样：在所有文件浏览器里按时间排序、靠谱地去重，以及让工具能把截图和同一天写的会议笔记对上。操作系统默认就会生成带日期的文件名，所以这条规则最省力的版本是：截图时顺手加两三个描述词，剩下的交给每周回顾兜底。

大文件走相反的规则：留在外面。视频、设计源文件、系统镜像不属于文本库——它们撑爆同步和备份，让 git 历史没法用，而且没有任何笔记渲染器能显示它们。界线大致画在几 MB：超过它，文件住在合适的地方——移动硬盘、对象存储、共享盘——笔记里放一个链接，而不是字节本身。笔记是索引，不是仓库；保持轻量的库，才能保持搜索快、备份便宜、搬迁不痛。

## 6. 从 Evernote 或 Notion 迁移：别弄断线头

迁移是纯文本押注兑现的地方，也是恐怖故事最多的地方，因为导出这一步正是两位在位者悄悄降低你所积累之物成色的环节。截至 2026 年 9 月，Evernote 桌面应用导出 ENEX——一种 XML 容器——或 HTML，没有原生 Markdown 选项；通往 Markdown 的路要经过 Yarle、evernote2md 这类社区转换器，它们把每条 ENEX 笔记变成一个 `.md` 文件，并把附件放进旁边的文件夹。Notion 依照其[导出文档](https://www.notion.com/help/export-your-content)提供按页或整库的 Markdown & CSV 导出，但拿回来的 Markdown 只是长得像 Markdown，上面全是 Notion 的指纹。两条路都不是一键的事，但都能在一两个下午内逃出来。

Evernote 的 ENEX 保住了内容——标题、日期、标签、HTML 正文、附件——但在转换之前没有一样东西是文件，而有些东西永远变不成文件。笔记间链接用的是 Evernote 自家的 `evernote://` 协议，转换即死，因为它指向应用而不是文档；预留一轮链接修复，把这些引用重建为笔记之间的普通链接——手动，但有边界。标签结构在大多数工具里能挺过转换，只是落地为纯文本，如果从未治理过，就会接着继承上一节的漂移问题。安全的操作顺序是：先转换、确认附件落地、修复链接、再套用命名规范——按这个顺序，因为每一步都让下一步看得更清楚。

Notion 的导出需要另一种预期管理。页面标题出来时，文件名和文件夹名里焊着 32 位十六进制 ID，页面间的链接被改写成相对这些带 ID 名字的路径——事后重命名任何东西，链接会再断一次。标注块、折叠块、同步块被拍平成普通文本；数据库导出成 Markdown 页面不包含的独立 CSV；而在大工作区上，导出任务本身在服务端排队，可能要等几个小时下载才就绪。这些都不构成否决——它们只是说明：导出物是原材料，不是成品库。

无论来源是什么，清洗这一轮长得都差不多，而且几乎全是脚本化的文本工作：一遍查找替换剥掉文件名上的 ID 后缀，修图片扩展名和链接，转换残留的 HTML 碎片，删掉各家工具撒在周围的导出样板。然后是唯一一轮真正重要的结构整理——趁上下文还热乎，把五题合一的巨无霸拆成一事一文，按规范重命名。迁移也是一个公平的时机，去发现哪些文档从来就不是笔记：比如一份简历，最舒服的形态是单个 [Markdown 简历源文件](/zh/blog/markdown-resume)，按需导出 PDF 和 Word，而不是任何应用里的一个页面。

这里有一条诚实的边界。如果一个 Notion 工作区主要是用关系型数据库做表格工作——筛选视图、汇总、公式——那么导出可能真的是降级，因为纯 Markdown 对数据库视图没有答案。文档迁移得很美；建在 Notion 里的应用不会。导出之前分清工作区里哪一半是哪一半，就是「解脱」和「后悔」的区别。

## 7. 每周回顾，十五分钟

上面每一条约定，没有维护循环都会衰减，而循环要活过糟糕的一周，前提是它足够小。十五分钟、每周一次、三趟——收件箱、链接、归档——这就是全部仪式。它借用了经典生产力每周回顾的骨架，改造后适配文件库：大部分检查要么靠眼睛，要么离一次搜索的距离。它能坚持下来的原因是无趣且限时：不靠英雄主义，也没有季度抢救周末。

这十五分钟有固定的形状，每一趟都有明确的终点线：

1. **清空收件箱（5 分钟）。** 停在收件箱文件夹里的每条笔记，拿到一个真名字、（如果和时间有关）一个日期前缀、至多两三个标签——或者被删除。没有任何东西能连续两次回顾还叫 `untitled.md`。
2. **闭合链接环（5 分钟）。** 把这一周想到但没打的那三四个链接补上，然后跑一次搜索，找出没有入链的笔记，把值得连的连上。
3. **向前归档（5 分钟）。** 属于已完结项目的笔记挪进 `archive` 文件夹——离开工作集，仍然可 grep——每月同一时段，顺路跑一遍上一节的标签审计。

换来的是一座从不堆积搁置决定的库。每条笔记每周保证被碰一次，足以在上下文还在脑子里的时候抓住一个起错名的文件，而不是隔着六个月的雾。每周十五分钟在心理上也比人们实际掉进去的那个替代品便宜——每年一次的「迁移到新应用」，动机多半是逃离上一个应用变成的烂摊子。归档值得拿到这里的最后一句：归档不是删除。archive 文件夹正是命名那一节里那些「五年后图景」的出处——还被活跃笔记链接着的笔记已经挣到了自己的位置；没有任何东西指向、也没有任何东西需要的笔记，是搬走的候选，不是哀悼的对象。

## 8. 换渲染器，不换内容

这套工作流的真正考验是迁移日。把文件夹拷到新电脑，换个应用打开，笔记照常渲染——标题、列表、表格、代码块完好无损。各渲染器之间有差异的是边缘部分：脚注语法、任务清单复选框、表格对齐。GitHub、Obsidian、Notion 对某些语法的渲染各有细微不同，值得在依赖某一个之前先知道。

安全规则：笔记正文保持在通用 Markdown 之内（标题、列表、表格、代码块、链接），把应用专属扩展当作可丢弃的装饰。当某个插件的奇特语法开始变得不可或缺，你又开始租房了。换到新渲染器发现哪里不对劲时，把文件贴进[浏览器端的 Markdown 工具](https://floatboat.ai/zh/tools/markdown)对比一下——五秒的渲染检查，好过迁移时的意外。

## 9. 让 AI 进入笔记库

这是 2026 年文件化笔记库真正甩开应用锁定型笔记的地方。能读取 `.md` 文件夹的 AI agent，可以像同事一样处理你的笔记：找出与某个客户相关的一切、总结一个月的会议记录、从历史决定里起草议程、或者标出相隔半年的两条笔记之间的矛盾。

设置过程毫无技术含量——这正是重点。没有导出管线，没有 API 集成，没有同步连接器。agent 直接读文件本身。[把 Obsidian 式笔记库接上 AI agent 的实操指南](/zh/blog/how-to-use-obsidian-with-ai-agent)讲了具体做法；[把笔记库当作 LLM 知识库的完整思路](/zh/blog/llm-knowledge-base-solo-operators)则解释了这笔投入什么时候值得：粗略地说，笔记过几百条、你开始问跨笔记问题而不是单笔记问题时。

两个习惯能让「AI 读笔记」的效果翻倍。第一，第 2 节说的标题纪律——agent 按标题切分和引用你的笔记。第二，一个文件一件事——检索质量在单条笔记混了五个话题时会明显下降，因为命中的那条笔记总会带着四个无关章节一起回来。

## 10. 今天就能开始的最小配置

入门门槛被刻意压得很低，而且值得一直压着：

1. 建一个笔记文件夹。像备份任何其他文件夹一样备份它。
2. 定一套命名规范——时间型笔记加日期前缀，主题笔记用纯名字。
3. 先用纯 Markdown 写下接下来十条笔记，再考虑任何定制。
4. 联想到关系时随手加链接。链接会复利，文件夹不会。

语法上的缺口，一页 [Markdown 速查表](/zh/blog/markdown-cheat-sheet)覆盖了笔记用得到的全部语法——标题、列表、表格、代码块。某条笔记需要确认视觉效果时，用[浏览器端的 Markdown 预览](https://floatboat.ai/zh/tools/markdown)打开，确认它读起来就是你想要的那个意思。

明天你打开的应用可以是 Obsidian、VS Code、某个手机 app，或者明年才发布的新东西。工作流——文件、命名、标题、链接——才是你拥有的部分。

## 11. 结语

Markdown 笔记与其说是一种工具选择，不如说是一次拒绝：拒绝把十年的思考存进一家公司拥有的数据库表结构里。这套工作流的成本是一个下午加几个习惯，扛得住每一次应用更替，在 AI agent 进入画面后变得更好，而且退化得体面——最坏的情况，是你的笔记是一堆用记事本就能打开的纯文本文件。

从一个文件夹、一条本来就要记的笔记开始。
