## TL;DR

- **Markdown 笔记工作流，就是把笔记保存为纯文本 `.md` 文件，靠命名规范、标题分层和笔记间链接来组织——不管当下用哪个应用渲染，笔记本身几十年后依然可读。** 工作流核心是三个习惯（一致的文件名、一个文件一件事、用链接代替文件夹），渲染器随便挑。
- 它消灭的失败模式是锁定：笔记应用会停服、被收购、改价格、导出成灾难。一个 `.md` 文件夹没有这些失败模式——[Markdown 是什么](/zh/blog/what-is-markdown)解释了为什么格式本身就是安全网。
- 核心工作流一个下午搭完：一个笔记文件夹、一套命名规范、文件内的标题结构，以及用链接代替深层文件夹的关联方式。
- 同一个笔记库可以直接变成 AI 工作区：能读取笔记文件夹的 agent，可以基于你已经信任的材料做摘要、交叉检索和起草。
- 从任何编辑器起步都行——文件优先，应用可换。

## 1. 纯文本笔记的 case

每一款笔记应用都做过同一个承诺：你的知识，永久有序。兑现记录参差不齐。服务被收购后关停、定价层级说变就变、私有数据库导出成灾难，而「导出」通常给你一份丢失了多年积累的链接和格式的 HTML 或 JSON。到 2026 年，笔记应用坟场已经大到让锁定风险成为选型的第一标准，而不是事后才想的细节。

Markdown 笔记押的是相反的方向。笔记就是一个文本文件。所有操作系统、所有编辑器、所有编程语言、所有 AI 模型都能读它。今天用的应用明天消失，笔记纹丝不动——换个工具打开，继续写。这个格式比大多数笔记应用都老，也会比它们全都活得久；Markdown 这一路是怎么走过来的，本质上就是「一个格式熬过一波又一波工具」的历史。

还有第二个更安静的优势：文件化的笔记可以 grep。当知识库是一个 `.md` 文件夹，全文搜索即时完成，备份就是复制文件夹，版本历史可以简单到只是一个 git 仓库。这些都不需要笔记应用批准。

## 2. 一套能熬过应用更替的工作流

工具不重要，习惯才重要。以下四个习惯决定了笔记库几年后还能不能用。

**一个文件一件事。** 一个叫 `2026-09-05 客户入职清单.md` 的笔记，胜过一个四百行、名叫「杂记」的文件。一个文件一件事，后面的链接、重命名、AI 摘要才成立——一个只说一件事的笔记，才能被单独链接、单独移动、单独喂给 agent，而不会拖出一堆不相关的内容。

**时间型笔记加日期前缀。** `2026-09-05 会议记录.md` 在任何文件浏览器里都按时间排序，零功能依赖。主题笔记（`markdown-工作流.md`）按字母排序，活在日期流之外。两种命名模式几乎覆盖所有场景。

**链接优于文件夹。** 深层文件夹逼你做选择——这条笔记归「客户」还是归「项目」？链接不需要做这个选择。一条笔记平铺在库里，可以被三个地方链接。在 Obsidian 一类的工具里，`[[双链]]` 一次按键完成；在纯 Markdown 里，指向文件的普通链接在所有地方都有效。如果你好奇 [Obsidian vault 到底是什么](/zh/blog/what-is-obsidian-vault)，一句话版本：一个 Markdown 文件夹，笔记之间的链接才是真正的结构，应用只是把它渲染出来。

**文件内部用标题，别只靠文件名。** `## 背景`、`## 决定`、`## 下一步`——一致的内部标题让一年后的笔记依然可扫读，也正是工具（和 AI）可靠地切分、引用你笔记的依据。

标签系统可以作为补充，但标签是最不可移植的一层：每个应用实现都不一样，有些还存在私有数据库里。链接和标题活在文件内部——这就是工作流依赖它们的原因。

## 3. 换渲染器，不换内容

这套工作流的真正考验是迁移日。把文件夹拷到新电脑，换个应用打开，笔记照常渲染——标题、列表、表格、代码块完好无损。各渲染器之间有差异的是边缘部分：脚注语法、任务清单复选框、表格对齐。GitHub、Obsidian、Notion 对某些语法的渲染各有细微不同，值得在依赖某一个之前先知道。

安全规则：笔记正文保持在通用 Markdown 之内（标题、列表、表格、代码块、链接），把应用专属扩展当作可丢弃的装饰。当某个插件的奇特语法开始变得不可或缺，你又开始租房了。换到新渲染器发现哪里不对劲时，把文件贴进[浏览器端的 Markdown 工具](https://floatboat.ai/zh/tools/markdown)对比一下——五秒的渲染检查，好过迁移时的意外。

## 4. 让 AI 进入笔记库

这是 2026 年文件化笔记库真正甩开应用锁定型笔记的地方。能读取 `.md` 文件夹的 AI agent，可以像同事一样处理你的笔记：找出与某个客户相关的一切、总结一个月的会议记录、从历史决定里起草议程、或者标出相隔半年的两条笔记之间的矛盾。

设置过程毫无技术含量——这正是重点。没有导出管线，没有 API 集成，没有同步连接器。agent 直接读文件本身。[把 Obsidian 式笔记库接上 AI agent 的实操指南](/zh/blog/how-to-use-obsidian-with-ai-agent)讲了具体做法；[把笔记库当作 LLM 知识库的完整思路](/zh/blog/llm-knowledge-base-solo-operators)则解释了这笔投入什么时候值得：粗略地说，笔记过几百条、你开始问跨笔记问题而不是单笔记问题时。

两个习惯能让「AI 读笔记」的效果翻倍。第一，第 2 节说的标题纪律——agent 按标题切分和引用你的笔记。第二，一个文件一件事——检索质量在单条笔记混了五个话题时会明显下降，因为命中的那条笔记总会带着四个无关章节一起回来。

## 5. 今天就能开始的最小配置

入门门槛被刻意压得很低，而且值得一直压着：

1. 建一个笔记文件夹。像备份任何其他文件夹一样备份它。
2. 定一套命名规范——时间型笔记加日期前缀，主题笔记用纯名字。
3. 先用纯 Markdown 写下接下来十条笔记，再考虑任何定制。
4. 联想到关系时随手加链接。链接会复利，文件夹不会。

语法上的缺口，一页 [Markdown 速查表](/zh/blog/markdown-cheat-sheet)覆盖了笔记用得到的全部语法——标题、列表、表格、代码块。某条笔记需要确认视觉效果时，用[浏览器端的 Markdown 预览](https://floatboat.ai/zh/tools/markdown)打开，确认它读起来就是你想要的那个意思。

明天你打开的应用可以是 Obsidian、VS Code、某个手机 app，或者明年才发布的新东西。工作流——文件、命名、标题、链接——才是你拥有的部分。

## 6. 结语

Markdown 笔记与其说是一种工具选择，不如说是一次拒绝：拒绝把十年的思考存进一家公司拥有的数据库表结构里。这套工作流的成本是一个下午加几个习惯，扛得住每一次应用更替，在 AI agent 进入画面后变得更好，而且退化得体面——最坏的情况，是你的笔记是一堆用记事本就能打开的纯文本文件。

从一个文件夹、一条本来就要记的笔记开始。
