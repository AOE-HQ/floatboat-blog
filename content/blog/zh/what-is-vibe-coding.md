你好，我是 Nova。上周我在整理书签——那些我发誓"晚点再读"的标签页，一如既往地乱——然后注意到一件事：我 2025 年初存进"有趣的 AI 玩意儿"文件夹的工具，一半不是死了、转型了，就是挂着一条安全事故公告。

大约就在那时我意识到：Vibe Coding 时代有一个非常喧闹的开场，而现在，它正在经历一场非常安静的清算。

我不是来宣布它已死的。但我是来给你一个诚实版本的：它是什么、它实际交付了什么、以及——最重要的是——如果你在经营一人业务，它对你意味着什么。

## 什么是 Vibe Coding？

### Vibe Coding 的白话定义

**Vibe Coding 是这样一种实践：用自然语言描述你想要的东西，让 AI 生成代码，从而构建软件。**你不写语法。你不读 diff。你描述一个结果，AI 产出它，你运行它——如果它能用，你就继续往前走。

这个名字抓住了那种感觉：你是跟着感觉走，不是照着公式走。你在引导，不是在工程化。

据[维基百科的 vibe coding 词条](<https://en.wikipedia.org/wiki/Vibe_coding>)，这种实践涉及"不做彻底审查就接受 AI 生成的代码，转而依赖运行结果和后续 prompt 来引导修改"。这是个公允的描述。也正是它让 Vibe Coding 对快速实验有用、对生产系统有风险的原因。

### 这个词从哪来

2025 年 2 月 2 日，AI 研究者、OpenAI 联合创始人 Andrej Karpathy [在 X 上发帖描述一种新的编程方式](<https://x.com/karpathy/status/1886192184808149383>)——你"彻底臣服于氛围，拥抱指数，甚至忘掉代码的存在"。他写道："我只是看到东西、说出东西、运行东西、复制粘贴东西，而且它大多能跑。"

一篇帖子。它能引起共鸣，是因为它给很多人在悄悄做的事命了名。柯林斯英语词典把 "vibe coding" 评为 2025 年度词汇。对一条推文来说，相当不错。

### 为什么这个词在流行

因为它描述了一个真实的转变。非开发者——创始人、运营者、内容人——一直在用 Cursor、Replit、Claude Code 这类工具交付小型自动化和内部工具。他们不是在"编程"。他们在 prompt、在验收。Vibe Coding 给这个现象命了名，对话由此爆发。

## Vibe Coding vs 传统开发

### 自然语言编程 vs 手写代码

传统开发意味着拥有每一行代码——具体的语法、具体的逻辑、具体的调试。你（理论上）理解每个部分做什么。

**Vibe Coding 把这套颠倒过来。**如 [Google Cloud 在其 vibe coding 概览中解释的](<https://cloud.google.com/discover/what-is-vibe-coding>)，这种方式"让你转而专注于想要的结果，用自然语言描述目标，由 AI 处理真正的代码"。主要角色从"写"变成了"引导"。

诚实版：这对简单、自包含的任务很有效。对任何触及复杂性、状态或安全的东西，效果就差一些。

### 速度 vs 结构：核心权衡

速度上去了——而且上去很多。一个以前交付不了 Web 工具的单人创始人，现在几小时就能让东西跑起来。结构下来了。生成的代码往往能用但脆弱：它处理得了你测过的那种场景，不一定处理得了你没想到的那种。

我想小心一点，别夸大其词。速度增益是真实且有意义的。权衡也是真实的。

### Vibe Coding 什么时候确实更好

对一次性工具、内部自动化、在投入前验证想法的快速原型——Vibe Coding 确实有用。Karpathy 最初把它框定为适合"一次性周末项目"。这个框定很要紧。它精确地告诉了你它为之设计的用例。

## 今天的单人创始人怎么用 Vibe Coding

### 没有开发团队也能建内部工具

这是最清晰的胜利。一个需要简单仪表盘、轻量 CRM、Slack 通知机器人的单人创业者——这些都是 Vibe Coding 能挣回本钱的正当用例。你不是在大规模给客户交付。你不是在处理敏感数据。你只是需要这个东西能用。

去年我用 AI 辅助搭了一个内容追踪工具。两个月里它每周帮我省约三小时。这是个真实的数字——不是我没用过就敢说的那种话。

### 自动化重复性工作流

**这是一人公司里 Vibe Coding 真正闪光的地方。**把表单提交连到电子表格更新、再连到 Slack 通知——这类以前需要懂 JavaScript 的任务——现在用 prompt 就能完成。"我希望这事自动发生"和"这事正在自动发生"之间的差距，已经变得非常小。

### 快速原型与想法验证

想在实际投入时间之前，测一测某个产品想法值不值得做？Vibe Coding 让这件事变便宜了。一位在 2025 年底开过 Vibe Coding 课程的哈佛教授，把它核心价值描述为改变"实验的经济学"——你可以做一个东西来理解一个东西，而且可以做得很快。这个框定我一直记得。并不是 Vibe Coding 能做出伟大的软件；而是它让实验变得负担得起。

## Vibe Coding 结束了吗？（为什么人们这么说）

### 反弹是从哪开始的

2026 年 2 月 8 日——他推广这个词整整一年之后——Karpathy 宣布 Vibe Coding 已经过时。[The New Stack 报道了他的发言](<https://thenewstack.io/vibe-coding-is-passe/>)：他现在更喜欢 "agentic engineering" 这个词：_"agentic，因为新的默认状态是你 99% 的时间并不直接写代码，而是在编排替你干活的 Agent、并充当监督；engineering，是为了强调其中存在一门技艺与科学，以及专业经验。"_

开发者的反弹在那之前就已经在积聚。到 2025 年年中，工程师们开始报告 Fast Company 所称的"Vibe Coding 宿醉"——团队接手了自己看不懂、没法调试、也不敢安全扩展的 AI 生成代码库。

### 来自开发者的常见批评

代码更替率上升 41%。代码重复量翻了四倍。而谨慎的重构——那种让代码库长期健康的功夫——从 2021 年占改动行数的 25%，掉到 2024 年的不足 10%。开发者 Simon Willison 说得很直白："如果 LLM 写了你代码的每一行，但你已经审查、测试并理解了全部内容，那不是 vibe coding——那是把 LLM 当打字助手用。"这个区别很要紧。

### "结束"对单人创业者真正意味着什么

我是这么看的。"Vibe Coding 已死"主要是一个关于"专业软件开发团队在大规模交付生产软件"的故事。对建内部工具或测想法的单人创始人来说，算账方式不同：风险画像更低，负责任地用这些工具所需的技能也更易获得。

话说回来——安全问题是真的，在把任何面向客户的东西发出去之前，值得了解。

## Vibe Coding 在哪里失效

### 没有清晰计划或结构时

模型用你给它的东西工作。prompt 含糊，输出就含糊。人类开发者可能会顶回来、问澄清问题，AI 不会——它会产出一个看起来像那么回事、但其实没解决你问题的东西。我生成过运行无报错、但做错事的代码。第三次之后，我开始把这叫做一个值得留意的模式。

### 输出需要长期维护时

更大的问题不是第一版，而是第五版。每一轮 prompt 驱动的迭代都会加入 AI 并没有完全追踪的复杂性。足够多轮之后，你最终可能得到一个技术上能跑、但没人（包括你）完全理解的东西。对任何要紧的东西来说，那都不是一个好地基。

### 系统变得过于复杂时

安全是 Vibe Coding 失效最清晰的例子。正如 [TechTarget 报道 AI 生成代码不断增长的风险时所说](<https://www.techtarget.com/searchapparchitecture/tip/Vibe-coding-is-killing-open-source-increasing-software-risk>)，代码更替与重复正随着安全债一起加速。OWASP 在 2025 年给它的 Top 10 加了一个专门类别，把"AI 辅助代码缺陷"明确标记为开发团队需要应对的一种模式。AI 生成的代码为功能性而优化，不是为安全性而优化。这不是同一个需求——而对一个团队里没有安全工程师的单人创始人来说，这个缺口可能在最糟的时机冒出来。

## 一人公司真正需要的替代品

### 从一次性产出到可复用的执行

按我的理解，真正的缺口在这里。Vibe Coding 给你产出——一个脚本、一个函数、一个小应用。而单人创业者真正需要的是**系统**：能可靠运行、可以交给协作者或"未来的你"、不会因为某个部件变化就坏掉的东西。

prompt 与工作流之间的区别，就是"问路"和"手里有张地图"之间的区别。

### 为什么系统思维比 prompt 更重要

问题不是"做这个任务最好的 prompt 是什么"，而是"我该怎么组织工作，让这个任务不再反复找上门"。这是一个运营问题。Vibe Coding 帮你执行一次任务。系统帮你彻底不再需要手动做这个任务。

### 把 AI + 运营 + 产品思维结合起来

我见过的做得好的单人创始人，不是 prompt 写得最好的那些人。他们是那种会审视自己的整个运营、然后问：_到底是什么在拖慢我？_再用 AI 去解决那个具体约束的人——而不是为了向自己证明 AI 能造出什么。

## Vibe Coding vs "Combo Skills"（真正的优势）

### 什么是 Combo Skills？

到这里我想提一件我一直在探索的东西：[Floatboat AI](</>)，一款引入了 **Combo Skills**概念的桌面工作区工具。

这个想法与 Vibe Coding 在结构上不同。不是"一个 prompt 产出一个输出"，Combo Skills 把多项 AI 能力——读文件、分析内容、生成结构、打磨输出——串成一条**可复用、可重复的工作流**。你把流程建一次，之后每次需要它就跑一次。

它更接近"搭一个系统"，而不是"执行一个任务"。这个区别正是全部重点。

### 为什么执行胜过纯粹的 prompt

好 prompt 和一个运转中的运营之间的那条鸿沟，恰恰是 Vibe Coding 没有解决的问题。prompt 一次产生一个东西；工作流每次都产生它，保持一致，遵循同样的标准。对单人创业者来说，**约束不在于能否用上 AI，而在于一致性**——你能不能在不必每次手动重做的情况下，复现自己最好的工作？

### 现代单人创始人的技能栈

据我过去一年的观察，那些在打造可持续一人业务的人，并不是在 Vibe Coding 和传统开发之间二选一。他们在组合：

  * **用 AI 换速度**——原型、起草、自动化重复性任务

  * **用系统思维换复利**——把工作结构化，让它随时间累积

  * **用判断兜底**——知道什么该审、什么该信、什么该质疑

你可以用 AI 工具构建，同时不放弃对你所建之物的理解。那才是真正值得培养的技能——而不是找到更好的 prompt。

![5.png](/blog/images/what-is-vibe-coding/1776318343607-e4c86648-6737-43e7-abf8-c58474b44c39.webp)

说实话，我自己也还在摸索。工具变化太快，三个月前我写的关于它们的东西，现在大概就需要更新了。而有一件事我确实越来越确定：**价值不在 prompt 里，在系统里。**那些在打造可持久运营业务的单人创始人，不是找到最好 AI 工具的人——而是建出能随时间复利的工作流的人。

这是想明白的一小块。
