采购 **AI Agent 开发服务**，首先不是选哪个大模型，而是决定由谁交付一套会读取企业数据、选择下一步、调用工具，甚至改动业务记录的软件系统。做出好看的演示并不难；真正难的是证明它能稳定完成真实工作、始终待在权限边界内，而且原开发团队离场后仍有人能运维。

市场上的“Agent 开发”可能指短期原型、自动化平台拼装、带模型工具调用的定制应用，也可能是套着咨询服务的托管产品。这些形式本身没有高下之分。问题在于，方案没有说清楚你买到的究竟是哪一种。

这篇指南面向正在比较外包团队、自由开发者、实施商与内部自建的采购者。文中不提供一个看似精确的“行业统一价”——需求、数据、权限和集成差异太大，这种数字并不可靠。我们更关心如何界定工作、比较证据、设计付费试点，并找出总报价背后的成本和风险。

## 先判断任务是不是真的需要 Agent

Anthropic 将 **工作流** 与 **Agent** 分得很清楚：工作流由代码预先规定路径，Agent 则由模型动态决定过程和工具使用。其官方建议同样克制：从最简单的方案开始，只有任务确实需要灵活判断时，才接受 Agent 带来的额外成本与延迟。可参考 [Anthropic 的 Agent 架构指南](https://www.anthropic.com/engineering/building-effective-agents)。

当输入、规则和异常都比较明确时，用确定性工作流通常更合适，例如按固定条件分发表单、同步已批准字段、根据稳定模板生成报告。只有当任务需要理解变化较大的输入、在多种工具之间选择、处理信息缺失，或在明确边界内决定下一步时，Agent 才可能体现价值。

询价前先回答五个问题：

1. 什么事件启动任务，怎样才算完成？
2. 哪些环节真的需要判断，而不是固定规则？
3. Agent 可以读取和改动哪些系统？
4. 哪些动作必须由人审批？
5. 证据不足、工具失败或置信度过低时怎么办？

如果团队还回答不了，就先买需求梳理或原型验证，不要直接签生产系统。

## 一项完整服务应包含什么

### 流程梳理与运行边界

需求阶段需要还原现有流程、任务量、异常分支、数据负责人和当前基线。交付结果至少应包括任务定义、成功与拒绝条件、动作与权限矩阵，以及待验证假设。服务商还应指出哪些步骤更适合保留为确定性逻辑。

### 架构与集成设计

设计图应标出模型层、编排逻辑、工具接口、状态存储、身份传递、审批节点、可观测性和部署边界，并用架构决策记录解释关键取舍。只写用了哪个框架，不等于给出了架构。

每个工具都要说明用途、可访问数据、允许动作、鉴权、超时与重试、速率限制和失败处理。读取与写入工具必须分开。发送消息、发布内容、退款、修改权限或业务主记录等高影响动作，应使用更窄的凭证并设置明确审批。

### 评估与验收

Agent 会连续执行多步、调用工具并改变状态，所以不能只看最终回答像不像。Anthropic 的 [Agent 评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 建议同时衡量任务结果、执行过程、可靠性和效率，而不是用一个笼统分数代替。

服务商应把真实任务整理成可版本管理的测试集，覆盖正常请求、含糊指令、数据缺失、工具故障、恶意指令，以及必须拒绝或升级给人的场景。验收标准应在开工前写清楚。

### 上线、运维与交接

生产范围应覆盖环境划分、发布与回滚、密钥管理、轨迹留存、告警、事故处理、模型或提示词变更，以及支持边界。交接不只是发一个源码压缩包，而应包含基础设施配置、运行手册、测试样本、依赖清单、数据流说明、管理员权限和接手培训。

## 写进工作说明书的交付物

| 阶段 | 阶段结束时至少应拿到的证据 |
|---|---|
| 需求梳理 | 流程图、现状基线、优先任务、数据分类、权限矩阵、风险清单 |
| 方案设计 | 架构图与数据流图、工具契约、模型选择理由、评估计划、成本模型 |
| 试点 | 受控环境中的可运行版本、版本化测试集、轨迹样本、失败分析、试点报告 |
| 生产上线 | 自动部署、监控告警、回滚方案、访问控制、事故处理手册 |
| 项目交接 | 源码与知识产权条款、系统文档、评估套件、凭证轮换方案、负责人培训 |

还要明确哪些内容**不在范围内**。数据清洗、安全审查、渗透测试、前端界面、第三方许可、模型用量、组织变更、上线支持和持续评估，经常会被单独计费。明确排除项，远比双方各自默认更安全。

## 怎么审查服务商给出的架构

不要奖励最复杂的图，而要看复杂度是否与任务匹配。

- **控制流：**哪些步骤留在代码里？哪些地方确实需要模型判断？
- **工具：**参数是否窄而可校验？权限能否撤销？危险参数能否在模型外强制约束？
- **状态：**单次运行、单个用户和长期状态分别存什么？错误记忆如何纠正、删除？
- **身份：**Agent 使用共享账号，还是代表具体用户行动？每个动作能否追溯？
- **审批：**哪些动作会停下来等人确认？审批人能看到哪些证据？
- **故障：**重试是否有上限？会不会重复写入？是否有幂等与回滚？
- **可迁移性：**提示词、轨迹、测试集、数据和工具定义能否导出？

看到多 Agent 架构时，先要求证明多角色确实提高了结果。增加 Agent 也会增加协调路径、延迟和排错难度。很多任务用单 Agent 配合清晰工具，甚至确定性流程加一次模型调用，反而更容易验证和运营。

## 安全与治理问题要在采购阶段提出

Agent 的风险来自模型行为、数据访问和行动权限的叠加。因此既要按 AI 系统审查，也要按企业应用集成审查。

NIST 的生成式 AI 风险画像用“治理、映射、测量、管理”组织全生命周期风险工作。它是自愿框架，但很适合分配责任人、整理控制证据。可查看 [NIST Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)。

要求服务商书面说明：

- 提示词、文件、工具结果、轨迹和反馈在哪里处理、保留多久；
- 数据是否用于训练，哪些子处理方能接触，以及数据区域、加密、删除和隔离；
- 最小权限、短期凭证、密钥存储和权限复核；
- 如何防范提示注入、检索内容投毒、工具滥用和意外泄露；
- 审计日志、安全测试、漏洞处置、事故通知与补丁责任；
- 高影响动作是否同时有人工审批与不可绕过的策略校验。

OpenAI 的企业 Agent 指南同样把护栏、受限数据源、真实世界动作前确认和审计轨迹视为系统要求。可阅读 [OpenAI 企业 Agent 指南](https://cdn.openai.com/business-guides-and-resources/a-business-leaders-guide-to-working-with-agents.pdf)。敏感或受监管业务应由内部安全、隐私、法务与业务负责人共同判断证据是否充分。

## 用什么指标验收付费试点

让候选团队拿到同一项有限任务、同一组代表性数据、相同约束和测试集。试点先在沙箱或只读权限下进行。

- **任务成功率：**完整满足验收条件，而不只是回答看起来合理。
- **严重错误率：**越权、不可逆、影响隐私或造成重大业务错误的动作单独设阈值。
- **升级质量：**能否在正确时机停下，并给人工足够上下文。
- **工具可靠性：**调用成功、重复动作、超时和部分失败处理情况。
- **人工复核负担：**每个完成任务需要多少复核时间与修改。
- **延迟与单位经济性：**包括重试和复核在内，每个成功任务的耗时与成本。
- **可追溯性：**审核者能否从日志与轨迹还原动作原因。

试点前先记录现有流程基线。如果报告只写“准确率 90%”，却没有定义计量单位、测试集、错误严重度和对照基线，就不是采购证据。

## AI Agent 开发服务怎么报价

常见形式有分阶段固定价、按工时、里程碑付款、专属团队和按月托管。

- **固定价**适合边界清楚的需求梳理或试点；不确定性高时容易变成频繁追加。
- **按工时**适合探索，但应设置预算上限、周度证据和决策门。
- **里程碑**应绑定已验收交付物和测试，而不是投入了多少工作。
- **托管服务**能转移运维，但更要关注服务等级、可迁移性和退出条款。

要求每家候选方分别列出需求、开发、集成、评估、安全、基础设施、模型用量、第三方许可、支持和变更费用。真正值得比较的是**每个成功任务的总成本**，不是一次性开发费。

内部可以用简化模型测算：

`年度价值 = 可覆盖任务量 × 单次改进价值 − 人工复核 − 运行成本 − 运维成本 − 预期失败损失`

每项使用区间，不要只填最乐观数字；还要算上维护集成、更新测试集和排查事故的人力。

## 合同里最容易漏掉的风险

正式协议应由合格法务审核。从交付角度，至少要解决：

- 源码、提示词、工具定义、评估数据、微调产物与文档的权利；
- 服务商可如何使用输入、输出、反馈与生产轨迹；
- 子处理方、数据区域、留存删除、事故通知和审计权；
- 模型、API 或平台变化由谁承担；
- 验收、整改期限、里程碑签字与终止权；
- 质保、赔偿、责任上限和禁止使用的高风险场景；
- 支持响应、变更费率和质保期终点；
- 退出包：最新源码、基础设施配置、数据结构、导出、测试集、运行手册和凭证轮换。

销售材料不能替代合同。如果某项要求在上线后仍然重要，就把它写进工作说明书或验收计划。

## 外包、自建，还是先从小方案开始

当任务价值明确、流程相对稳定，所需集成或风险控制超过内部能力，而且公司有一位真正负责决策和接手的负责人时，外部服务比较合适。

当 Agent 将形成核心差异化、工作流频繁变化，或者内部已经具备工程、安全、数据和运维能力时，可以考虑自建。自建不等于免费，只是把成本与责任留在组织内部。

当流程仍在变化、动作风险较低且常见，或业务尚未记录现状基线时，先用现成产品、工作流工具或小原型验证。若要继续判断架构深度，可阅读[定制 AI Agent 开发的真实取舍](/zh/blog/custom-ai-agent-development)；如果目标是重复性知识工作，可按[重复工作 Agent 构建指南](/zh/blog/how-to-build-ai-agents-for-repeated-work)先缩小首个任务。

## 一套可执行的服务商筛选流程

1. 用一页纸写清任务边界、负责人、现状基线和审批节点。
2. 明确第一笔采购是需求梳理、试点、生产交付，还是托管结果。
3. 给所有候选方同一份需求，要求相同的交付物和报价拆分。
4. 查看真实架构材料、脱敏评估报告和交接包，而不只是演示。
5. 向客户证人询问故障、需求变更、上线支持和退出过程。
6. 用自己的代表性案例，在沙箱中运行限时付费试点。
7. 只有安全审查通过、指标达到验收线、负责人明确，而且回滚与退出方案都测试过，才批准生产上线。

值得选择的 AI Agent 开发服务商，不是承诺“最自主”的那一家，而是能证明哪里需要自主、哪里必须受限、效果如何衡量，以及交付后你的团队如何继续掌控系统的那一家。
