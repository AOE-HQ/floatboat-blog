ChatGPT Space 是 ChatGPT 里的持久工作空间，用来集中管理可编辑的 Pages、上传文件、文件夹和协作内容。它要解决的并不是「对话不够长」，而是另一个更实际的问题：讨论结束后，真正要交付和长期维护的那份文档放在哪里？

理解 Space，可以先把几个容易混淆的东西拆开：Chat 用来讨论，Page 是可直接编辑的文档，Space 负责组织相关 Pages 与文件，Project 继续保存项目聊天、资料与专属指令。Agent 可以参与起草和修改 Page，但 Space 本身不会因此自动变成持续运行的 Agent。

截至 2026 年 10 月 10 日，OpenAI 官方说明中，Space 的创建与编辑面向 ChatGPT Pro、Business 和 Enterprise。具体能否共享、可以共享给谁，还会受到组织管理员设置、账号角色和地区可用性的影响。

## 别把聊天记录当成最终交付物

设想一次产品发布讨论。对话里既有可用的结论，也有被否定的方案、临时追问和多个版本的措辞。把整段聊天发给同事，并不能让对方立即知道哪一版才有效；他仍要重新梳理上下文。

Space 提供了另一种落点：把已经确认的目标、决策和下一步整理为一张 Page，直接修改正文，再把会议纪要、调研和周报放到子页面。审核者可以针对某句话留言，编辑者可以改正文，其他人也能让自己的 ChatGPT 帮忙处理同一份共享材料。大家围绕 Page 审阅，而不是在聊天记录里考古。

OpenAI 的 [Space 入门说明](https://help.openai.com/en/articles/20001549-getting-started-with-space-in-chatgpt) 将 Page 定义为可编辑文档，可以承载表格、图表、追踪器、互动工具、文件和子页面。官方同时提醒，分享前仍要核对姓名、日期、计算结果和来源。AI 参与生成不等于内容自动可信，Page 仍然需要正常的文档审核。

## Chat、Page、Space、Project 和 Agent 各管什么

如果只看它们都能「放资料、调用 ChatGPT」，这些功能很容易显得重叠。真正的差别在于，哪个对象才是工作的中心。

| 对象 | 工作中心 | 更适合处理 | 不应误解为 |
|---|---|---|---|
| Chat | 一段对话 | 探索问题、追问、一次性任务 | 持续维护的正式文档 |
| Page | 一份可编辑成果 | Brief、计划、研究结论、会议纪要、团队说明 | 作者私人聊天与 Memory 的共享入口 |
| Space | 一组相关 Pages、文件和文件夹 | 围绕主题或团队组织长期内容 | 自动执行系统或 Projects 的替代品 |
| Project | 项目聊天、文件、来源和项目指令 | 多轮对话反复使用同一组限定上下文 | 可分层维护的文档树 |
| Dot 或其他 Agent | 执行者 | 在获准的上下文和工具中调研、撰写、修改或继续任务 | 自动拥有 Space 的全部权限 |

Page 与 Project 的边界最值得单独说明。OpenAI 当前的 [Projects 文档](https://help.openai.com/en/articles/10169521-projects-in-chatgpt) 把 Project 描述为持续变化的上下文中心：项目里的聊天可以使用共用文件和专属指令，成员也能继续发起新对话。Space 更关注可维护的成果本身。

例如，团队可以在 Project 中多轮讨论品牌定位，让不同对话继续使用同一批材料；确认后的定位文档则适合进入 Page，由成员共同编辑。两者可以配合，但官方明确保留了 Projects。Space 只是在获得使用资格的账户中替代 Library，并不会把既有 Project 自动转换成 Space。

## Space 相比 Library 真正多了什么

Library 更像「ChatGPT 产生或接收过哪些文件」的存放入口。Space 在存放之外增加了一套内容组织和共同编辑机制：

- Page 可以直接撰写和修改，而不只是作为附件被保存；
- 一个 Space 可以包含文件夹、多张 Page 和普通文件；
- Page 能继续嵌套子页面，让摘要与支撑材料形成层级；
- 协作者可以针对局部内容评论，也可以共同编辑；
- 每个人用自己的 ChatGPT 或当前可用的 Agent 处理共享内容。

这里有一个容易被宣传语省略的限定：官方说的是 Space 会替代**已获得 Space 权限账户中的 Library**，不是所有 ChatGPT 账户已经统一迁移，也不是 Library 中的每个文件都应该变成 Page。

迁移时应按内容职责判断。图片、原始 PDF 或数据文件可以继续作为支撑材料；需要持续修订、多人评审和反复引用的项目说明、决策记录和研究结论，才是更合适的 Page 候选。如果把所有旧文件原样搬入，最终只会得到一个结构更复杂的新文件柜。

## 在 Page 里调用 Agent，不等于开启了自动维护

Page 为 AI 协作提供了多个入口。大范围修改可以先在页面旁边的对话里讨论；一句话或一个段落需要调整时，可以选中文字发起请求；具体审核意见可以留在评论里；当前账户有 dot 时，也能在正文或评论中提及它。

OpenAI 的 [Space Agent 使用指南](https://learn.chatgpt.com/docs/space/agents) 建议根据任务选择入口，并在继续之前审核 Agent 的回复和页面改动。一个比较稳妥的分工是：

1. 尚未确定改法时，先在旁侧对话中探索，不直接覆盖正文；
2. 修改范围明确时，选中对应文字，避免 Agent 顺手重写无关章节；
3. 审核意见需要保留讨论脉络时，在评论中发起；
4. 只有特定 Agent 掌握所需指令或工具时，才明确提及它。

Space 上线时并不支持 Keep Updated 自动更新。仅仅在 Page 中写下「每周刷新一次」，不会自动生成定时任务。周期性工作必须在其他入口完成调度，再核对任务是否已保存、是否启用以及实际运行结果。[AI Workspace Agent](/zh/blog/ai-workspace-agents) 讨论的正是这层执行能力：工作空间提供上下文与成果落点，Agent 才负责推进任务。

## 三类适合 Space 的工作

### 把探索过程沉淀为决策记录

研究型任务往往先经历很多问答。真正需要留下来的，通常不是全部对话，而是当前结论、采用依据、来源和未决问题。团队可以从对话创建 Page，把已确认判断放在主页面，把证据和待办放入子页面。

供应商评估、竞品调研、政策说明和内容 Brief 都适合这样处理。反过来，如果支撑材料不能向 Page 的读者公开，或者组织要求正式记录只能保存在既有文档系统中，就不应为了使用 Space 强行改变权威版本的位置。

### 围绕一份文档完成审阅

在可用角色范围内，Page 可以授予查看、评论或编辑权限。评论者围绕具体段落提出意见，编辑者直接更新正文；协作者使用自己的 ChatGPT，不会因此继承页面所有者的私人对话。

这套方式成立的前提，是团队明确哪一份 Page 是当前有效版本。如果每个人仍然导出副本、在线下修改、再把结果贴回去，Space 只会增加一个版本源，无法消除版本混乱。

### 为重复工作维护一个小型知识树

主 Page 可以保存当前计划，下面按需要建立会议纪要、决策记录、每周进展和来源材料。读者先看摘要，需要追溯时再进入子页面，适合兼顾「快速了解现状」与「查看依据」的工作。

但内容结构清楚，不代表工作已经会自动执行。周期性抓取、日历触发、跨系统写入或主动提醒仍然需要持续 Agent、定时任务或其他自动化机制。[Agent Connector](/zh/blog/ai-agent-connectors-explained) 决定执行者能访问哪些外部系统，与 Space 如何组织文档是两层问题。

## 权限最容易出错的地方是「继承」

Space 的访问权并不只来自一张 Page 上的直接邀请。根据 OpenAI 的 [Space 协作指南](https://learn.chatgpt.com/docs/space/collaboration)，共享一个 Space 会让成员访问其中 Pages；共享父 Page，也会把访问权传给子页面。因此，同一个人可能通过直接邀请、父 Page 或所属 Space 获得权限。

这会带来两个常见误区：

- 移除某人的直接邀请后，他可能仍通过上级页面或 Space 保留访问；
- 把 Page 移动到另一个父页面下，可能同时改变它的可见范围。

所以，重组目录之前不能只考虑「放在哪里更整齐」，还要检查权限树。包含客户信息的子页面，不应仅因为主题相近就移动到面向更大团队共享的父页面下。

文件权限还有另一套规则。直接上传到 Page 的文件跟随 Page 权限；只是链接到其他位置的文件，不会因为 Page 被共享而自动开放。Google Drive 等外部服务仍执行自己的访问控制。然而，一旦用户或 Agent 把原文件内容摘要、复制到 Page，能够查看 Page 的人就能看到这些衍生内容，即使他们打不开原始文件。

换句话说，来源私密不代表写入共享 Page 的结论仍然私密。

## 私人聊天没有共享，私人信息仍可能进入 Page

把 Page 分享出去，不会让别人直接访问你的私人聊天或 ChatGPT Memory。风险发生在内容被写入 Page 的那一刻：如果 Memory 已开启，ChatGPT 在协助写作时可能调用先前对话中的个人背景；这些背景一旦出现在 Page 正文中，就对所有有权查看 Page 的人可见。

OpenAI 的 [Space 数据与控制说明](https://help.openai.com/en/articles/20001544-chatgpt-space-sharing-data-and-controls) 还指出，每位协作者使用共享内容时，适用的是他自己的 Memory 与模型训练设置。对于个人账户，你关闭「帮助改进模型」，并不能替另一位协作者关闭他的设置。OpenAI 表示，ChatGPT Business 和 Enterprise 的业务数据默认不用于训练。

因此，团队的数据检查至少要覆盖五个问题：

- Agent 可能把哪些私人上下文写进 Page？
- 哪些人会通过父 Page 或 Space 继承权限？
- 上传文件是否真的适合相同受众？
- 协作者的 Agent 是否可能记住共享内容？
- 这次交互适用个人账户设置，还是组织的数据与保留策略？

涉及敏感资料时，还需要按实际套餐、地区和组织政策核对保留、数据驻留与合规要求，不能只根据一篇产品介绍做安全结论。

## 当前开放范围和上线限制

下面是 OpenAI 文档截至 2026 年 10 月 10 日列出的主要边界：

| 能力 | 官方当前状态 |
|---|---|
| 创建和编辑 Space 内容 | ChatGPT Pro、Business、Enterprise |
| Web 与桌面端 | 可创建、编辑、组织和共享 |
| 移动端 | 可查找、阅读、共享和浏览层级，不能编辑 Page |
| Slides 与 Sheets | 即将推出 |
| Keep Updated 自动更新 Page | 上线时不可用 |
| 受管理工作空间共享 | 受组织设置控制；Enterprise 管理员可能需要主动开启 |
| 加拿大或阿联酋数据驻留的 Business/Enterprise | 官方列为即将推出 |

如果工作必须在手机上编辑、以电子表格为主，或要求 Page 自动刷新，现阶段的 Space 就不是完整替代方案。同一套餐的两位用户看到不同的共享选项也不一定是故障，账号角色与管理员政策都可能收窄可用范围。

## 迁移前先做一个小范围闭环

不要先把全部 Library 文件、Projects 资料或本地文档搬进去。挑一条有代表性的工作流，用以下步骤验证 Space 是否真的能成为新的维护入口。

### 先指定唯一权威版本

确定 Page、Project 来源和外部文档中，究竟哪一个可以被编辑并视为最终版本。其余位置只做来源或快照，不同时维护三份主稿。

### 把讨论与交付物分开

聊天保留探索过程，Page 只承接已经接受的决策、当前计划和需要长期维护的说明。不要为了「完整」把大量无效讨论重新塞回文档。

### 先画受众，再搭页面层级

列清楚哪些内容面向核心团队、跨部门成员或外部协作者，再决定父 Page 与子 Page 的关系。Space 里，内容树同时也是权限设计的一部分。

### 用第二个账号测试来源访问

让试点协作者打开 Page，并逐一验证外部来源。看得到 Page，不代表能打开其中的 Drive 文件、其他 Space 文件或连接应用链接。

### 测试撤权，而不只是邀请

完成一次邀请、降权和撤销访问，检查对方是否仍通过父 Page 或 Space 获得权限。只有验证过移除路径，权限模型才算真正跑通。

### 把 Agent 修改当作正式文档变更

核对日期、姓名、数字、来源，以及 Agent 实际改动了哪些段落。AI 只是参与编辑，不应跳过团队原有的审核责任。

### 在设为唯一副本前确认退出路径

先确认关键内容如何导出、备份或转移，再决定是否只保存在 Space。受监管记录、代码文档和有正式留存要求的材料尤其需要这一步。

## 什么情况下不该选 Space

如果团队需要的是一份可以与 ChatGPT 共同维护、评论并按层级组织的可读成果，Space 很合适。常见场景包括研究集合、项目计划、团队手册、会议后续和多轮评审的草稿。

如果重点是让多轮**对话**始终使用固定文件与指令，Project 更直接。正式审批、成熟修订历史和企业记录管理是刚需时，既有文档系统通常仍是权威入口。代码与仓库文档依赖 diff、分支、自动检查和本地工具，也应继续留在版本控制中。

敏感源文件或正式成果必须留在用户掌控的设备上时，可以进一步比较 [本地优先与云端 Agent 工作站](/zh/blog/local-first-vs-cloud-agent-workspace)。Floatboat 采用本地文件可见、模型与 Agent 围绕文件工作的路线，不要求把云端 Page 作为唯一长期副本。这是对成果所有权和工作边界的另一种选择，并不意味着所有任务都应留在本地。

## 真正要选择的是「成果放在哪里」

ChatGPT Space 不只是 Library 换了名字。它把保存的内容变成可以直接编辑、分层组织、多人评审，并由 ChatGPT 或其他可用 Agent 协助处理的 Pages。但它也不是一套完整的自主工作系统：Projects 仍然独立，Keep Updated 上线时不可用，权限会从上层继承，外部来源继续执行自己的访问规则。

因此，决定是否采用 Space 时，不必先问「新功能值不值得用」。更有效的问题是：当前有效版本应该保存在哪里，谁有权修改，Agent 可以从哪些来源带入信息，以及出现权限或迁移问题时如何退出。能够回答这四件事，再从一条工作流开始试点，比一次性迁入全部资料更稳妥。
